# Onboarding v2

## Purpose

A refined, continuous connection experience for the Proton VPN Windows app. Evolves v1 into a single cinematic flow with four states that animate seamlessly into one another. The user sees their real exposed data, protects themselves with one click, watches the VPN take effect in real time, then picks what matters most (JTBD) and gets country-specific context.

## Status

In Progress — all four states implemented and wired as a continuous flow. Reachable from the start screen via the "Onboarding v2" button.

## Stages

The end-to-end flow is sliced into four named stages (`OnboardingStage` / `ONBOARDING_STAGES` in `OnboardingV2.tsx`). The first three are phases inside the `OnboardingV2` state machine; the fourth is a separate modal shown once in the main app.

| Stage | Name | Phases | Lives in |
|-------|------|--------|----------|
| 1 | **Establishing VPN connection** | `unprotected` → `connecting` → `protected` | `OnboardingV2.tsx` |
| 2 | **Personalized JTBD tuning** | `jtbd` → `tuned` | `OnboardingV2.tsx` |
| 3 | **Upgrade to Plus** | `upsell` → `checkout` → `plus-welcome` | `OnboardingV2.tsx` |
| 4 | **Final personalization** | — (`MakeYoursModal`, not a phase) | `App.tsx`, `components/MakeYoursModal.tsx` — see "Final personalization modal" below |

`PHASE_STAGE` maps each phase to its stage and is used internally (e.g. `dim`/`isProtectedSide` on the map) instead of long per-phase OR-chains. Render sections in `OnboardingV2.tsx` are marked with `Stage N:` banner comments matching this table.

## States / Key User Flows

`Unprotected → Connecting → Protected → JTBD Selection → Tuning → Tuned Result → VPN Plus Upsell → [Checkout Loader → VPN Plus Welcome] → App transition → "Make Proton VPN yours" modal`

1. **Unprotected** — Dark map centered on the user's real location. Coral open-padlock header, danger headline, ISP warning. Red pulsating pin framed by an animated sci-fi targeting reticle (`TargetingReticle`). Glassmorphic info card (3 rows: country+flag, IP, ISP). CTA: "Protect my online identity".
2. **Connecting** — Spinner header, "Protecting your online activity....". Background gradient morphs coral → slate. Reticle fades out, pin turns gray, map slowly zooms out. Card values progressively redact to asterisks (labels stay readable). VPN connect is simulated (min 3.2s).
3. **Protected** — Teal closed-padlock header, "...now fully protected!". Gradient morphs slate → teal. Map flies to the VPN server (Netherlands). Teal pulsating pin wrapped in an animated protective shield aura (`ShieldAura`). Info card rebuilds to 4 staggered rows (location hidden, appears-in country+flag, IP hidden, VPN IP in teal). CTA: "Continue".
4. **JTBD Selection** (`JtbdGridPanel`) — a centered 3×2 grid of 6 selectable JTBD tiles (icon + label), a small contextual "wink" line + idea-bubble illustration once a tile is picked, and a dynamic Continue ("Continue" → "Tune for {jtbd}" once selected) + top-right Skip. Picking a tile again deselects it. Continue advances straight to `tuned` (no separate loader — see below); Skip exits.
5–6. **Tuned Result** (`TunedResult`, phase `tuned`) — a single, consolidated result step with no separate loader: opens with its own centered intro (see "Header intro/move/counter" below) that becomes the result header, then the 5 settings materialize one at a time into the selected **layout** (Stacked / Split by Status / Card Grid / Compact List — see "Tuning-stage layouts" below), then completes with a "Tuned for {jtbd}" title, a derived summary subtext, and Continue. **No tip** anywhere on this screen (removed across all 4 layouts). Top-left Back button returns to JTBD selection. Plus users (`userPlan="plus"`) see all 5 items as applied (no locked items, no tier-boundary widget).
7. **VPN Plus Upsell** — Split-screen conversion screen. "Get VPN Plus" → checkout loader; "Continue free" → exit.
8. **Checkout Loader** — Transparent overlay reusing `LoaderScreen` (same teal gradient background). Title "Completing checkout...", subtitle "Confirming your payment. This takes a few seconds." 3000ms fixed timer (no real API), then advances to Plus Welcome.
9. **VPN Plus Welcome** (`PlusWelcomeState`) — Renders the same 5-item tuned result in whichever of the 4 **result layouts** (Stacked / Split by Status / Card Grid / Compact List) the shared "Layout" selector currently has active — see "Stage 3 reuses stage 2's layouts" below. All 3 free items render active from the start; the 2 previously-locked paid items transform locked → unlocked at ~600ms settle (badge crossfades to green check, text brightens, "Available" value pill slides in where that layout's own resolved design shows one, "Just unlocked" chip), positioned per layout (last 2 rows / right column / bottom 2 cards). Both transform with a 200ms stagger. Confetti fires once. **No tip** (removed, matching the Tuned Result step). Continue ("Start using VPN Plus") fires `onEnterApp` (hands off to the main app — assumes VPN is already connected to Netherlands from earlier in the flow).

**The upsell screen** (`VPNPlusUpsell`). Left (~52%): "What VPN Plus unlocks for you" heading, JTBD-personalized subheading, 3 JTBD-specific benefit cards (green check + outcome + "via {feature}" + (i) tooltip), an italic "everything else" line, a factual trust-signal row, and two CTAs. Pricing is folded into the primary CTA: "Get VPN Plus" with a concise second line ("$4.99/mo, billed yearly · save 50%"); the secondary ghost "Continue free" stays clearly available. Right (~48%): black panel with the 3D ▽+ hero image bleeding to the edges. A top-left Back button returns to the Tuned Result. Content density is tuned to fit the 768px window without scrolling. Uses Tailwind container queries (`@container`): below ~900px panel width the hero is hidden and content goes single-column. Both CTAs currently exit. Lucide icons (Info, ArrowUpRight, ShieldCheck, BadgeCheck, RefreshCw); Radix Tooltip on (i) icons.

## Data Model

- **`GeoInfo`** (`lib/useIpDetection.ts`) — live IP detection via `ipwho.is` with a Figma-matching fallback (Lithuania / Orange / 158.6.140.191). Fields: `ip, country, countryCode, city, isp, lat, lng`. The real country is captured before connecting and reused for the JTBD panel (the VPN is active by then and would otherwise report the server country).
- **`VPN_SERVER`** (`lib/server.ts`) — fixed "fastest" server (Netherlands / Amsterdam / `146.70.124.18`).
- **JTBD context matrix** (`lib/jtbdData.ts`) — 6 jobs × {UK, US, Germany, France, Netherlands, fallback} factual copy.
- **JTBD wink copy** (`JTBD_WINK_COPY` in `lib/jtbdData.ts`) — one short, knowing line per JTBD, shown by `JtbdGridPanel` next to the idea-bubble illustration once a card is picked. With the user, never at them; no capability-overclaiming; no emoji.
- **JTBD Continue-label copy** (`JTBD_CONTINUE_LABEL` + `JTBD_CONTINUE_LABEL_DEFAULT` in `lib/jtbdData.ts`) — the grid picker's primary CTA text: `JTBD_CONTINUE_LABEL_DEFAULT` ("Continue") pre-selection, one full "Tune for {jtbd}" string per JTBD once picked (not runtime-concatenated, so each locale can adapt word order / the "access" mapping for "Bypass restrictions" naturally).
- **JTBD tuning result** (`lib/jtbdTuningResult.ts`) — per-`JtbdId` tuning outcome (`JTBD_TUNING_RESULT`): `jtbdLabel`, exactly 3 `enabled` features (`outcome`, `settingsName`, `value`, `tooltip`), exactly 2 `paid` features (`outcome`, `featureName`, `asset`, `tooltip`), and a `tip` (string | null). Single source of truth for the Tuning/Tuned screens — no copy is hardcoded in components. Every feature has a short hover `tooltip`; `privacy.tip` is `null` pending confirmation.
- **JTBD upsell** (`lib/jtbdUpsell.ts`) — per-`JtbdId` upsell content (`JTBD_UPSELL`): `jtbdWord` (subheading injection) + exactly 3 `benefits` (`outcome`, `featureName`, `learnMore`, `tooltip`). Plus `UPSELL_PRICING`, `UPSELL_EVERYTHING_ELSE`, `UPSELL_TRUST_SIGNALS`. Single source of truth for the upsell screen. Pricing/trust values are verified against Proton's public June-2026 pricing/policy (monthly $9.99, 30-day money-back guarantee, Swiss-based, independently audited no-logs); `[UNVERIFIED]` the yearly $4.99/mo is design-confirmed but Proton's current public 1-yr rate is $3.99/mo — confirm region/promo before shipping.

## Content variants (Unprotected → Connecting → Protected)

The first three states support interchangeable content variants via the `variant` prop on `OnboardingV2` (`"v1" | "v2" | "v4" | "v4-split" | "hybrid" | "hybrid-split"`, **default `"hybrid"`** — both `OnboardingV2`'s own default and `App.tsx`'s initial `variant` state), selectable from the prototype-controls "Version" dropdown (grouped as `CONNECTION_GROUPS` — "#1 Location map spotlight" {`v1` Centered / `v2` Split}, "#2 Browsing experience" {`v4` Centered / `v4-split` Split}, "#3 Hybrid" {`hybrid` Centered / `hybrid-split` Split}). Onboarding now opens on "#3 Hybrid" / Centered by default; any group/layout is still freely selectable from the dropdown. v1–v2 share the map, pin, reticle, shield aura, gradients, and choreography (`ENTRANCE_TIMING`) and differ only in copy + info-card content; v4/v4-split are a self-contained, map-less concept variant (see below); Hybrid combines both, with its own Centered/Split layouts (see below). States 4+ (JTBD onward) are unchanged across all variants. **v3 ("Take back what's yours"), v5 ("The Watchers"), and v6 ("The Mirror") were retired** — their main title + subtitle (from v3) were ported into v4 before removal (see below); their component files were deleted.

- **v1 — Original**: threat framing. "Your online identity is currently unprotected" + live data card (country/IP/ISP) + "Protect my online identity".
- **v2 — "You're in control" (side control panel, `ControlPanelOverlay`)**: distinct **asymmetric layout** — a solid left rail (~400px, `rgba(22,20,28,0.85)` + blur) acts as a dashboard, and the map is **offset right** so the pin sits centered in the remaining region (`OnboardingMapV2.focusOffsetX`). Rail: padlock/spinner → headline → subtext → a "Visible on this network:" list of the exposure facts → CTA docked at the bottom. Copy: "Let's make this connection private" / "Setting up your private connection…" / "Done — you're private now". CTA "Make me private" → "Securing…" → "Continue".
- **v4 — "In Plain Sight" (open diary, `versions/v4-in-plain-sight/`)**: map-less single centered column. Everyday internet life logged as a diary. Main title + subtitle are **ported verbatim from the retired v3**: "Your online life is more visible than you'd think" / "On this network, others can see the everyday things you do." **5 curated, archetypal, relatable entries** (`data/activityEntries.ts`) type in one at a time (~42ms/char, blinking caret, ~1.1s apart, starting only after the header settles), each shows an eye + "Visible" — the app never reads real history. Entrance order: padlock → title → subtitle → diary entries one by one → CTA (`V4_TIMING.padlockAppear/headlineAppear/subtextAppear/feedStart`). The top status gradient is flipped (`scaleY(-1)`) to match the main app's convention, reading strongest at the top and fading downward. On connect entries redact oldest-first (asterisk scramble) with a synchronized `FeedScanline`, eyes → crossed-out eyes (a custom mark, not a Lucide icon — see `ActivityEntry.tsx`'s `EyeHiddenIcon`) with status "Hiding…" → "Hidden" (straightforward tone; other tones use their own words); protected act tints the mark teal, slides in a teal seal card ("From now on, this is all they see."), headline "Your diary is sealed." + confirmation footer. CTA "Make it unreadable.".
- **Hybrid — combined concept (`versions/hybrid/`)**: see "Version Hybrid" below.

Supporting changes: `InfoCard` gained optional `heading`, `footnote`, and per-row `icon` (`label` is now a `ReactNode`); `OnboardingMapV2` gained `focusOffsetX` (shifts the pin's on-screen position right for v2) and `focusOffsetY` (shifts it down/up, negative = up; used by Hybrid — see below); shared `Padlocks` component (`PadlockOpen`/`PadlockClosed`) extracted for reuse. `OnboardingV2` branches the states-1–3 overlay by variant (v1 inline centered layout; v2 dedicated overlay component; v4/Hybrid self-contained full-cover/transparent overlays) — the phase state machine, persistent map, connect timing, and states 4+ are shared and unchanged. v4 is map-less and renders an opaque backdrop that covers the persistent map during stage 1; Hybrid (like v1/v2) is a transparent overlay that lets the persistent map show through.

### Version v4 (new concept variant, no Figma)

v4 lives under `src/app/onboarding-v2/versions/v4-in-plain-sight/` and implements the shared `StageOneVersionProps` contract (`versions/types.ts`): `{ phase, geo, isLive, onProtect, onContinue, copy }`. It reuses the parent phase machine + 3.2s connect simulation (satisfies the ≥2.5s connecting hold; there is no real connect service, so no 15s timeout/retry exists to reuse). No i18n framework exists in the repo, so all copy is passed in via the `copy` prop (a `BrowsingCopy` object selected by tone — see "Tone of voice" below); `data/activityEntries.ts` keeps only the tone-invariant diary `ACTIVITY_ENTRIES` (icons/category/base text). No analytics infrastructure exists, so stage events are not fired. All diary content is archetypal (never the user's real history). Ships a `prefers-reduced-motion` variant (simple fades — no typewriter/scanline) and centralizes timing in `V4_TIMING`. Perpetual motion is CSS transform/opacity; one-time entrances use Framer Motion.

Shared version helpers (`versions/lib/`): `useReducedMotion`, `scramble.ts` (`useScramble`/`maskAll` — a local generalization of `useProgressiveMask`, kept separate so the shared hook is untouched), `ConnectionBackdrop` (reuses `StatusGradient`), `ConfirmationFooter` (VPN flag + country + VPN IP).

### Version Hybrid — combines map-spotlight + browsing experience

`versions/hybrid/` merges the two other groups into one three-act scene (Centered and Split layouts — `hybrid` / `hybrid-split`), reusing as much as possible rather than reimplementing: `Hybrid.tsx` (Centered orchestrator), `HybridSplit.tsx` (Split layout — same content/timing, different arrangement), `useHybridReveal.ts` (the card reveal/redact/connect-timeout sequencing shared by both layouts, since it's layout-independent), `LocationChip.tsx` (the one genuinely new visual element, reused by both layouts), `timing.ts` (`HYBRID_TIMING`). Both layouts take the same minimal props shape as v1/v2 (`{ phase, geo, isLive, onProtect, onContinue, tone }`), not `StageOneVersionProps` (they don't need a `BrowsingCopy` object — see "Tone of voice" below for how Hybrid gets its copy instead).

**What's reused, unchanged, and why nothing needed to be imported for it:** `OnboardingMapV2` (map, pulsating pin, `TargetingReticle`, `ShieldAura`, top `StatusGradient`) is rendered **once** by `OnboardingV2`, shared across every stage-1 variant and driven purely by the same `phase`/`geo`/`stage` values `OnboardingV2` already computes generically — Hybrid is simply another transparent overlay on top of it (like v1/v2), so the map/pin/reticle/aura/gradient/flyTo/spinner needed **zero new code**. `ActivityEntry` (from `versions/v4-in-plain-sight/`) is reused directly, unchanged, for the 3 activity cards — same component, same `useScramble`-driven redaction, same `ACTIVITY_ENTRIES` data (the first 3 of the 5 curated entries). The real VPN "connect" is the same shared `handleProtect` in `OnboardingV2` every version already calls via `onProtect`.

**What's new:** `LocationChip` — a rounded-pill {flag} {country} · {IP} element. Act 1 shows the real (`useIpDetection`) country/IP, with a skeleton while `!isLive` (mirroring the same loading idiom `InfoCard`/`MaskedValue` use, without reusing that component's row-based markup, which doesn't fit a pill). Act 2 scrambles the country name and IP to asterisks via the same `useScramble` hook the cards use (200ms after connecting starts, so it reads as coordinated with the map's flyTo and the cards' redaction, not sequential); the flag fades rather than scrambling (nothing to redact in an icon). Act 3 crossfades the pill's *inner content* (not the pill container, which stays mounted throughout) to the resolved VPN identity from `VPN_SERVER` (country/flag/`vpnIp`, IP in teal) — `useScramble` can only mask/unmask its own input text, not resolve to a *different* value, so the value-swap is a straightforward AnimatePresence crossfade of the inner span, the same "persistent container, swapped inner content" idiom used elsewhere in this codebase (e.g. `InPlainSight`'s headline swaps). Also new: `useHybridReveal` (the small local reveal/redact-sequencing state for the 3 cards — `ActivityFeed`, the diary's own orchestrator, hardcodes all 5 entries with no count prop, so it wasn't reusable for "3 cards" as-is — reusing the card component directly and writing new, centralized sequencing for it is the explicitly-scoped-in "new orchestration" piece).

**Split layout (`HybridSplit.tsx`, key `hybrid-split`):** same content, data and `HYBRID_TIMING` pacing as Centered (via the shared `useHybridReveal`), rearranged into a left rail + right panel at an even **50/50 width split** (`w-1/2` each — a deliberate departure from the map-spotlight split's 400px/v2 and the browsing split's 380px rail widths, both narrower-rail conventions) — the left rail holds icon/title/subtext/**activity cards**/CTA vertically centered as one group (the cards sit between the subtext and the CTA, reserving a fixed `min-h-[164px]` — matching Centered's own reservation — so the CTA doesn't drift down as cards reveal progressively), and the right panel holds **only** the location chip, anchored in its **lower half** (the panel is split into two equal flex regions; the top is left empty for the pin, the chip is centered within the bottom one) so it reads as below the pin without needing to measure the pin's exact position. Unlike the browsing split (map-less, opaque), Hybrid's right panel stays **transparent** — the persistent map + pin show through, offset right via `OnboardingV2`'s `splitFocusOffsetX` (256px for the 50/50 rail, vs. v2's 200px for its 400px rail — both simplify to `railWidth / 2`, centering the pin in the remaining region) so the pin lands in that same visible area. No vertical pin *measurement* is attempted in Split (unlike Centered) — matching the map-spotlight split's own precedent, which doesn't center the pin against its rail content either; only Centered needs that, since only there does the pin sit in a dedicated gap between two specific elements.

**Continuity across acts:** the map is never unmounted (owned entirely by the parent, outside Hybrid); the chip is one persistent `motion.div` whose inner content crossfades; the 3 cards are the same `ActivityEntry` instances throughout (`key={entry.id}`, never phase-keyed) — only their `redact`/`sealed` props change. Icon and title/subtext use `AnimatePresence mode="wait"` keyed by phase for a true overlapping crossfade (a slightly higher-fidelity treatment than v1's own header, which fully remounts `key={phase}` on every transition).

**Opening entrance order (Act 1):** map pin (the shared map's own `ENTRANCE_TIMING.pinAppear`/`bracketsStart`, unchanged) → location chip → padlock icon → title → subtext → activity cards (one at a time) → CTA. Unlike v4 — which reuses `ENTRANCE_TIMING`'s padlock/headline/subtext beats directly since its order matches v1's — Hybrid's chip-before-icon order doesn't, so its icon/title/subtext delays are Hybrid's own values in `HYBRID_TIMING` (`padlockAppear`/`headlineAppear`/`subtextAppear`/`chipAppear`), not `ENTRANCE_TIMING`'s.

**Pin vertical centering:** the title and subtext slots each reserve a fixed `min-h` (worst-case line count across all three acts' copy) so the block's bottom edge — and therefore the gap available for the map/pin below it — never shifts between acts (previously, hiding the subtext during Act 2, or a headline wrapping differently, would reflow everything below it). `Hybrid` then measures (via `getBoundingClientRect` + a `ResizeObserver`, `useLayoutEffect`) the actual gap between that stable header bottom and the top of the `LocationChip`, and reports the offset needed to center the pin in it through `onPinOffsetChange`, which `OnboardingV2` feeds into `OnboardingMapV2.focusOffsetY`. This is measured, not a hardcoded constant, so it stays correct regardless of exact font metrics or copy length.

**Tone of voice:** Hybrid is fully wired into the same axis as v1/v2/v4/v4-split (see "Tone of voice" below) rather than having its own dedicated, tone-agnostic copy. `CONNECTION_COPY[tone]` gained a third shape, `hybrid` (`HybridCopy`: `exposedHeadline`/`exposedSub`/`connectingHeadline`/`protectedHeadline`/`protectedSub`/`ctaProtect` — the map-spotlight-shaped half of the layout), alongside the existing `mapSpotlight` and `browsing`. The 3 activity cards' `visibleLabel`/`redactingLabel`/`sealedLabel` are **not** duplicated into `hybrid` — Hybrid reads those straight from `browsing` per tone, since the cards are the literal same reused `ActivityEntry` component. `straightforward.hybrid` preserves Hybrid's original copy verbatim (so the default experience is unchanged); the other three tones are fresh Hybrid-specific wording in the same voice as their `mapSpotlight` counterparts (not copy-pasted, to avoid two tones showing identical text within Hybrid itself).

**Known gaps, inherited from the source versions (not introduced by Hybrid):** no real connect service and no existing timeout/retry UI pattern exist anywhere in the repo to reuse — the simulated connect is a fixed ~3.2s `setTimeout`, so `HYBRID_TIMING.connectTimeoutMs` (15s) is a defensive hold-with-shimmer safeguard that can't currently fire, with no "Retry" action wired (there's no real failure to retry from). Neither `OnboardingMapV2` nor any existing version has reduced-motion handling for the map/flyTo itself; Hybrid's `prefers-reduced-motion` variant covers everything it controls (chip scramble, card scramble/typewriter, icon/title crossfades — via the shared `useReducedMotion`) but inherits the map's un-reduced flyTo, same as v1/v2 do today.

## Tone of voice (content axis — Stages 1 & 2)

A third prototype-controls dropdown, **"Tone of voice"**, rewrites copy **content only** — every layout, concept, animation and timing is untouched. It is orthogonal to the Version/Layout selectors, so any of the five connection layouts (Location map spotlight Centered `v1` / Split `v2`; Browsing experience Centered `v4` / Split `v4-split`; Hybrid Centered) — or, for stage 2, any of the 4 result layouts — can be rendered in any tone. The axis is `ToneOfVoice` (`"straightforward" | "reassuring" | "empowering" | "educational"`, `lib/toneOfVoice.tsx`), backed by a single **global** `tone` state in `App.tsx`, threaded down through the `tone` prop on `OnboardingV2` to whichever stage/variant is active. The dropdown is shown only for stages listed in `STAGE_SUPPORTS_TONE` — originally connection-only; **stage 2 ("tuning") now opts in too**, exactly per the pattern's own design intent ("the structure is deliberately generic so other stages can opt in later: add their copy shape here and add the stage to `STAGE_SUPPORTS_TONE`"). This confirms the selector was always meant to be one global control with per-stage opt-in visibility, not a separate mechanism per stage.

### Stage 1 (connection)

All connection copy lives in `CONNECTION_COPY[tone]`, split into `mapSpotlight` (headline/subtext/CTA/split-view card headings for `v1`/`v2`, with phase-colored accent spans and ISP interpolation), `browsing` (the `BrowsingCopy` object for `v4`/`v4-split`: headlines, sub, CTA, connecting/protected headlines, seal card, continue, `visibleLabel`, and the per-entry lock labels `redactingLabel`/`sealedLabel`), and `hybrid` (the `HybridCopy` object for Hybrid: `exposedHeadline`/`exposedSub`/`connectingHeadline`/`protectedHeadline`/`protectedSub`/`ctaProtect` — Hybrid's cards reuse `browsing`'s `visibleLabel`/`redactingLabel`/`sealedLabel` rather than duplicating them). `OnboardingV2` reads `mapSpotlight` inline for `v1`/`v2`, passes `browsing` down as the `copy` prop to the diary components, and passes `tone` straight through to `Hybrid` (which reads `hybrid` + `browsing` itself); `ActivityFeed`/`ActivityEntry` take `redactingLabel`/`sealedLabel` as props (previously hardcoded "Protecting…"/"Protected"; the straightforward tone's values are now "Hiding…"/"Hidden", to match the crossed-out-eye icon rather than the earlier padlock-style wording). The tone-invariant diary entries themselves and the data-row labels ("Your IP address:", etc.) are deliberately unchanged across tones.

The four tones:
- **Straightforward** (default — the original shipped copy): factual, calm, professional. e.g. "Your online identity is currently unprotected" / diary card mark "Hiding…" → "Hidden".
- **Reassuring**: warm, empathetic, peace-of-mind. e.g. "Right now, this connection isn't private" / CTA "Make my connection private" / lock "Securing…" → "Private".
- **Empowering**: agency and control. e.g. "You decide who sees you online" / CTA "Take control" / "You're back in control" / lock "Claiming…" → "Yours".
- **Educational**: expert clarity, explains the mechanism. e.g. "Here's what your network can see" / CTA "Encrypt my connection" / "Your traffic is now encrypted" / lock "Encrypting…" → "Encrypted".

### Stage 2 (tuning)

Every copy surface across the picker + tuned-result step is tone-aware: `JtbdGridPanel`'s title/subtitle; the tuned-result header's intro subtext, the "{verb} for {jtbd}…"/"{verb} for {jtbd}" title pair, and the completion summary; and every JTBD's 3 enabled + 2 paid feature **outcome** sentences and its **tip**, across all 4 layouts and all 6 JTBDs.

**Structural copy** — `TuningCopy` (`lib/toneOfVoice.tsx`), a `Record<ToneOfVoice, TuningCopy>` named `TUNING_COPY` (unrelated to, and a full replacement for, the *different*, now-deleted `TUNING_COPY` that used to live in `versions/lib/tuning.ts` before the tuning-stage consolidation — pure naming coincidence, no shared history):
```ts
interface TuningCopy {
  pickerTitle: string;
  pickerSubtitle: string;
  introSubtext: string;
  titleDuring: (jtbdWord: string) => string;
  titleComplete: (jtbdWord: string) => string;
  summarySubtext: (applied: number, locked: number) => string;
}
```
`JtbdGridPanel` reads `pickerTitle`/`pickerSubtitle` directly from `TUNING_COPY[tone]`. `tuned-result/copy.ts`'s `introSubtext`/`titleDuring`/`titleComplete`/`summarySubtext` functions were changed to take a `tone` parameter and delegate into `TUNING_COPY[tone] ?? TUNING_COPY.straightforward` (the fallback-to-straightforward on a missing tone every tone-aware function in this stage implements). `counterSubtext` ("Applying X of N settings") took no `tone` parameter change — it's one of the strings kept constant (see below).

**Per-JTBD copy** (outcomes + tips) — a *separate* file, `lib/jtbdTuningToneCopy.ts`, a sibling of the base `lib/jtbdTuningResult.ts` it re-voices: `JTBD_TONE_OUTCOMES: Record<ToneOfVoice, Record<JtbdId, JtbdToneOutcomes>>` where `JtbdToneOutcomes = { enabled: [string,string,string]; paid: [string,string]; tip: string | null }`, mirroring the base data's tuple shape/order exactly. Deliberately NOT folded into `toneOfVoice.tsx` — cramming 6 JTBDs' worth of outcome sentences into that file would break the "one file per content concern" convention every other data file here follows (`jtbdData.ts`, `jtbdUpsell.ts`, etc.); `straightforward`'s entries are *built directly from* `JTBD_TUNING_RESULT`'s existing `outcome`/`tip` fields (not hand-copied) so the two can never drift. Two lookup helpers, `toneOutcome(tone, jtbdId, "enabled"|"paid", index)` and `toneTip(tone, jtbdId)`, both fall back to `straightforward` on a missing tone. The base data (`settingsName`/`value`/`featureName`/`asset`/`tooltip`) is **never** re-voiced or touched — only the plain-language `outcome`/`tip` text changes.

**Wiring into the layouts:** all 4 (`StackedLayout`/`CompactListLayout`/`SplitByStatusLayout`/`CardGridLayout`) gained a `tone` prop. `StackedLayout` (whose resolved row JSX is bespoke, not `EnabledFeatureRow`/`PaidFeatureRow`) calls `toneOutcome(...)` directly in place of `feature.outcome`. The other three reuse `EnabledFeatureRow`/`PaidFeatureRow` verbatim (unmodified, per scope) — since those components read `outcome` straight off the `feature` object passed to them, each layout builds a `{ ...feature, outcome: toneOutcome(...) }` shallow copy immediately before rendering, so only the outcome text is swapped and every other field (settings name, value, feature name, asset, tooltip) passes through completely untouched. The tip lookup (`toneTip`) exists as data for completeness (the task's copy matrix explicitly asked for it) but isn't rendered by any current layout — matching the base `JTBD_TUNING_RESULT.tip` field's own status, which was already unused after the tip footnote was removed from every result screen (see below); reintroducing a Tip UI was out of scope for this change.

**Confirmed CONSTANT across all 4 tones** (checkpoint): the 6 JTBD option labels (`JTBD_OPTIONS`), technical settings names/values/feature names/decorative assets (all of `JTBD_TUNING_RESULT` except `outcome`/`tip`), the "Available with VPN Plus" badge + Split by Status column headers (`TUNED_RESULT_COPY`), the counter format ("Applying X of N settings"), the picker's witty "wink" line (`JTBD_WINK_COPY`), the per-row narration verbs ("Enabling…"/"Checking…", `narrateEnabling`/`narrateChecking`), and the neutral navigation labels (Skip, Back, the pre-selection "Continue", and the dynamic "Tune for {jtbd}" CTA, `JTBD_CONTINUE_LABEL`) — this last group mirrors stage 1's own precedent, where `browsing.continue` is likewise the literal string `"Continue"` in all 4 tones; only the more expressive/emotive strings vary by tone in either stage.

**Analytics:** no analytics infrastructure exists anywhere in this repo (confirmed again during this change) — consistent with every other tone-aware surface, no events are fired for tone changes.

## Tuning-stage: single consolidated flow + result layouts

The "Personalized JTBD tuning" stage was **consolidated from 5 separate versions into ONE flow**, formerly the "Visual Tuning" version's mechanics — picker → no separate loader → a result step that opens with its own centered intro and materializes its 5 settings one at a time. The 5 selectable JTBD-tuning versions that used to exist (Default, Loadouts, Split by Status, Card Grid, Visual Tuning) are gone as *versions*; three of their result designs survive as **result LAYOUTS** of the one consolidated flow — Loadouts did not survive in any form (it was a fully self-contained morphing-card scene with no reusable result "arrangement" concept, and nothing else in the codebase depended on it or its `TuningStageVersionProps` contract, confirmed before removal). The bottom prototype selector that used to pick a "Version" for this stage now picks this **Layout** instead.

**Files removed in the consolidation:** `JtbdPanel.tsx` (the old two-column radio-list picker — `JtbdGridPanel` is now the stage's only picker), `components/TuningLoaderState.tsx` (the separate "Tuning the app for you…" loader — no longer used by anything), `components/TunedResultState.tsx` (the old "Default" result screen), `versions/tuning-loadouts/` (entire folder), `versions/tuning-split-by-status/`, `versions/tuning-card-grid/`, `versions/tuning-visual-tuning/` (the latter three's designs live on as `tuned-result/layouts/*` instead — see below), and `versions/lib/tuning.ts` (`TuningStageVersionProps`/`JTBD_ORDER`/`TUNING_COPY`, used only by Loadouts). `EnabledFeatureRow`/`PaidFeatureRow` were **kept unchanged** — they're still reused both by the new layouts and by the untouched, downstream `PlusWelcomeState`.

**The tip footnote was removed from every result-style screen** (`TunedResult` — all 4 layouts — and `PlusWelcomeState`, since it re-shows the same content). `components/TuningTip.tsx` was deleted (it had no other callers left); `JTBD_TUNING_RESULT`'s `tip` field is left in the data unchanged (still populated per-JTBD) but is simply never read by any component now. `useTunedMaterialization`'s `continueDelayMs` no longer waits on a tip gap — Continue fades in directly after the last item resolves.

### The single flow

1. **Picker** (`JtbdGridPanel`, phase `jtbd`) — unchanged from before this consolidation (3×2 grid, wink message, dynamic Continue label, toggle-to-deselect). `onContinue` now unconditionally advances straight to phase `tuned` — there is no `tuning` (loader) phase left in the `Phase` type at all.
2. **Result step** (`TunedResult`, phase `tuned`, `src/app/onboarding-v2/tuned-result/TunedResult.tsx`) — the sole result component, parameterized by a `layout: ResultLayout` prop (`"stacked" | "split-by-status" | "card-grid" | "compact-list"`, default `"stacked"`). Runs, identically for every layout:
   - **Centered intro** — the header block (loader `Spinner` + "Tuning for {jtbd}…" + a static "Applying the settings to optimize the experience for you." subtext) fades in centered on screen and holds there for `centerHold` (2000ms).
   - **Move to top** — the SAME block (one persistent `motion.div`, Framer's `layout` prop drives the FLIP from a `justify-center`→`justify-start` wrapper toggle, never unmounted) travels to its top position over `moveToTop` (600ms); the spinner crossfades (true overlap, not sequential) into the JTBD's category icon (`JTBD_ICONS`, same fixed 48×48 slot, no size jump) and the subtext crossfades to the live "Applying {X} of {N} settings" counter. Reduced motion skips the travel animation entirely (renders top-anchored from the start; `layout` disabled) and only holds briefly (`reducedIntroHold`, 500ms) before the same crossfades fire.
   - **Materialization** — only once the block has landed do the 5 settings items begin their two-phase reveal, one at a time (Phase 1: narrated spinner "Enabling {setting}…"/"Checking {feature}…"; Phase 2, ~300ms: resolves into the finished visual). The counter's X is `rowMounted.filter(Boolean).length` — derived directly from the same row-progression state the items render from (no separate counter variable), incrementing the instant each item's Phase-1 spinner is scheduled (both free and locked items count, 1..5). A free/paid **boundary beat** (an extra pause, `boundaryIn + rowGap`) is reserved before the first locked item begins in every layout's timing, even layouts (Card Grid) that don't render a visible widget there — this keeps total pacing identical across all 4 layouts, per the "centralize timing in one shared config" requirement.
   - **Completion** — once the last item resolves, the title crossfades to "Tuned for {jtbd}" (same sentence structure as the "during" form, just the verb/ellipsis change, so it reads as a simple word swap) and the subtext to the derived "{applied} settings applied · {locked} available with VPN Plus" summary (the "· {locked}…" clause is dropped entirely, not shown as "0 available", for Plus users); Continue fades in and becomes interactive. No tip footnote anywhere in this step (removed across all 4 layouts — see below). `{jtbd}` is `result.jtbdLabel.toLowerCase()` throughout — already the project's agreed gerund short form for bypass ("Bypassing restrictions"), so no separate lookup table is needed.
3. `OnboardingV2` keys `<TunedResult key={resultLayout} .../>` by the selected layout, so **switching the Layout selector remounts the whole component and replays the sequence from the centered intro** in the newly chosen arrangement — confirmed as the desired prototype behavior (so reviewers can see the full intro + materialization in any layout, not just its static end state), rather than jumping straight to a completed state.

Only the RESOLVED ARRANGEMENT of the 5 items — and which "shape" their Phase-1 placeholder takes — differs per layout; the intro, header move, counter, completion strings, and Continue are 100% shared, driven by one hook (`useTunedMaterialization`) and one timing config (`TUNED_RESULT_TIMING`, in `tuned-result/timing.ts`) with no per-layout timing overrides.

### Stage 3 reuses stage 2's layouts (shared "Layout" selector)

Stage 3's Plus-welcome result (`PlusWelcomeState`, state 9) renders in the SAME 4 layout components as stage 2's `TunedResult`, fed a `layout: ResultLayout` prop — **no separate selector**: `resultLayout` is (and always was) a single state lifted to `App.tsx`, threaded through `OnboardingV2` to both `TunedResult` and `PlusWelcomeState` — the prototype-controls "Layout" dropdown now appears (and is enabled) for both the "tuning" and "upgrade" stages, changing the same underlying value from either one (`STAGE_VERSIONS.upgrade` mirrors `STAGE_VERSIONS.tuning`'s 4 options; `usesResultLayout` in `App.tsx`'s `PrototypeControls` covers both stages).

Unlike stage 2, `PlusWelcomeState` skips materialization entirely — all 5 items are passed as already `"resolved"` (`rowStages`/`rowMounted` are constant arrays, not driven by `useTunedMaterialization`) — and passes each layout a new optional prop, `unlockTransition?: { unlocked: boolean; showChip: boolean }`. This is the ONLY behavioral branch added to the 4 layout components; when omitted (stage 2's call sites), behavior is byte-for-byte unchanged. When present:

- All 3 free items render in their normal active state (unaffected).

- Stacked's own paid row is bespoke (not one of `EnabledFeatureRow`/`PaidFeatureRow`'s 3 shapes), so it has its own equivalent inline transform in `StackedLayout.tsx` (same choreography/timing, reusing `TransformingPaidCell`'s exported `UnlockedChip`).

- `paidUnlocked` is passed as `true` (the settled/eventual value — every layout's boundary-widget-hiding logic, e.g. Stacked/Compact List's divider, already reacts correctly to a Plus user) while `unlockTransition.unlocked` is the separate LIVE, animated value driving the crossfade itself.

`PlusWelcomeState` owns only what's genuinely stage-3-specific: the "Welcome to VPN Plus" / JTBD subheading header, the confetti (`Confetti.tsx`, unchanged), the timers driving `unlocked`/`showConfetti`/`showChip` (now reading `TUNED_RESULT_TIMING`'s `unlock*` constants instead of local consts), and the "Start using VPN Plus" CTA. ## Unprotected entrance animation ("surveillance lock-on")

The Unprotected screen plays a cinematic ~4.5s entrance on mount. The screen starts as the dark map only (everything else hidden) and reveals element by element while the map zooms toward the user. All timing lives in `lib/entranceTiming.ts` (`ENTRANCE_TIMING`).

Timeline (T=0 = mount):

| T (ms) | Element | Motion |
|--------|---------|--------|
| 0 | Map | Starts at world view (zoom 2), `flyTo` user coords (zoom 5) over 3500ms (Leaflet) |
| 500–2000 | Status gradient | Fades 0→1 (Framer) — danger tint creeps in |
| 1500 | Pin | Springs in (scale 0→1, overshoot) via CSS `ob2-pin-in` |
| 2000 | Pin pulsation | Concentric rings begin (CSS animation-delay) — not before |
| 2000 | Reticle | Animated targeting reticle scales/fades in (overshoot), then its layers animate continuously |
| 2500 | Padlock | Fade + drop from above |
| 2800 | Headline | Fade + slide up |
| 3100 | Subtext | Fade + slide up |
| 3200 | Info card | Rises from below |
| 3400 | Card rows | Stagger in 150ms apart (explicit per-row delays) |
| 4000 | CTA | Rises + scale; perpetual breathing glow (CSS `btnGlow`) |

Implementation notes:

- The map's `flyTo` starts at T=0 to the seeded fallback coords; when live IP detection resolves with different coords, a second `flyTo` (1.6s) redirects. The map never waits for the API.
- Pin entrance + pulsation gating are pure CSS (no setTimeout): the spring uses `animation-delay` = `pinAppear`; the pulse ring uses `animation-delay` = `bracketsStart`.
- `OnboardingMapV2` skips the first reactive run of its fly/status effects (`flyInit`/`statusInit` refs) so the mount entrance is not overridden.
- Info card shows skeleton bars (`loading` = unprotected && `!isLive`) and crossfades to real values when live data arrives. CTA is disabled (opacity 50%) until `isLive`.
- Per-phase delays are conditional: only `phase === "unprotected"` uses the long entrance delays; later phases use a quick stagger so transitions stay snappy.

## Phase-transition Choreography

- **Unprotected → Connecting** (button click): button scales/fades out; gradient coral→slate; padlock→spinner; reticle fades out (250ms); scramble starts +400ms; map zoom-out begins.
- **Connecting → Protected** (VPN confirmed, min 3.2s): spinner→lock; gradient slate→teal; `flyTo` server; teal pin; card rows stagger in; Continue fades in after.
- **Protected → JTBD** (Continue): centered overlay fades out; map dims; left column slides in from -40px, right from +40px.

## Stacking / z-index (important)

Leaflet assigns its internal panes z-index values of 200–700 (tilePane 200 … markerPane 600 … popupPane 700). Any overlay rendered as a sibling of the map must sit above this range or it will be painted over by the tiles (symptom: content flashes once, then the map covers it). v2 handles this by:

- isolating the Leaflet container with `isolation: isolate` so its pane z-indices stay contained, and
- rendering the centered overlay and the JTBD panel at `z-[1000]`, the title bar at `z-[1200]` (matching v1's convention).
