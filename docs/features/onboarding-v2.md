# Onboarding v2

## Purpose

A refined, continuous connection experience for the Proton VPN Windows app. Evolves v1 into a single cinematic flow with four states that animate seamlessly into one another. The user sees their real exposed data, protects themselves with one click, watches the VPN take effect in real time, then picks what matters most (JTBD) and gets country-specific context.

## Status

In Progress — all four states implemented and wired as a continuous flow. Reachable from the start screen via the "Onboarding v2" button.

## Stages

The end-to-end flow is sliced into four named stages (`OnboardingStage` / `ONBOARDING_STAGES` in `OnboardingV2.tsx`). The first three are phases inside the `OnboardingV2` state machine; the fourth is a separate modal shown once in the main app.

| Stage | Name | Phases | Lives in |
|-------|------|--------|----------|
| 1 | **Establishing VPN connection** | `unprotected` → `connecting` → `protected` | `OnboardingV2.tsx` |
| 2 | **Personalized JTBD tuning** | `jtbd` → `tuned` | `OnboardingV2.tsx` |
| 3 | **Upgrade to Plus** | `upsell` → `web-checkout` → `checkout` → `plus-welcome` | `OnboardingV2.tsx` |
| 4 | **Final personalization** | — (`MakeYoursModal`, not a phase) | `App.tsx`, `components/MakeYoursModal.tsx` — see "Final personalization modal" below |

`PHASE_STAGE` maps each phase to its stage and is used internally (e.g. `dim`/`isProtectedSide` on the map) instead of long per-phase OR-chains. Render sections in `OnboardingV2.tsx` are marked with `Stage N:` banner comments matching this table.

## Connection failure path

Stage 1's `unprotected → connecting → protected` phases assumed success — there was no designed path for a connection that fails. A three-tier failure path now covers this, added on top of a new `"failed"` `Phase` value (`OnboardingV2.tsx`), version-agnostic (shared by all 6 connection-stage versions, implemented once).

**Checkpoint 0 finding (gates the whole design):** the connect "service" is a pure `setTimeout` simulation (`CONNECT_MS`/`HAPPY_PATH_CONNECT_MS = 3200`) with **no error model at all** — it always succeeds, exposes no error codes/exceptions, not even a generic timeout. No cause is genuinely detectable. Every tier/cause below is therefore demoed via a deliberate **prototype HUD simulation** (`FAILURE_SIM_PRESETS`, `lib/connectionSimulator.ts`) rather than derived from real detection — confirmed at checkpoint before building anything.

**Simulation layer** (`lib/connectionSimulator.ts`, `lib/connectionFailureConfig.ts`, `lib/useConnectionAttempt.ts`):
- `FailureCause`: `"no-internet" | "vpn-conflict" | "permission" | "network-blocks-vpn" | "generic"`. The first three genuinely require the user (no auto-remedy could plausibly fix them), so their simulated sequence is a single attempt before Tier 2. The last two ARE things a different server/connection method might route around, so they run the full 3-slot Tier 1 sequence (`sequenceLengthFor`).
- `ResolvePoint`: `"immediate" | "remedy1" | "remedy2" | "tier2-retry" | "never"` — which attempt/slot finally succeeds, chosen by the HUD preset.
- `FAILURE_SIM_PRESETS` — 4 presets (`App.tsx`'s "Simulate connection" HUD dropdown, connection stage only): `"none"` ("Successful connection") plus one per user-required cause (`no-internet`/`vpn-conflict`/`permission` — "No internet"/"Another VPN running"/"Permission problem", each `resolvesAt: "never"`, demoing the full three-tier journey through to the auto-exit/deferred-onboarding path). Simplified from an earlier, broader preset list (confirmed at checkpoint) that also covered `network-blocks-vpn`/`generic`'s auto-resolving Tier-1 remedies and per-cause "retry succeeds"/"retry fails" variants — those causes/remedies remain fully intact in the underlying model (`sequenceLengthFor`, `willSucceedAtSlot`), just no longer exposed as their own HUD presets.
- `useConnectionAttempt` (React hook) owns the entire attempt lifecycle. On the happy path (`cause: null`) it is **byte-for-byte the original behavior** — a single `HAPPY_PATH_CONNECT_MS` (3200ms) timer, no narration, no "Still trying…" — guaranteeing this feature never touches success-path timing. Once a failure is simulated, each attempt runs `CONNECTION_FAILURE_TIMING.attemptTimeoutMs` (8000ms), with a `stillTryingThresholdMs` (5500ms) reassurance line, respecting `maxAutoRemedies` (2).

**Tier 1 — silent auto-remedy, no error screen.** While `phase === "connecting"`, a failed attempt (for `network-blocks-vpn`/`generic` causes) retries with a different country, then with Stealth + Alternative Routing enabled — both simulation-only parameters the user never sees named (`CONNECTION_RETRY_NARRATION.remedy1`/`remedy2`: "Trying a different location…" / "Trying a different way to connect…", overriding the connecting-state headline). A "Still trying…" line appears additively once any single attempt passes the threshold (`ConnectingNarration`, reused by every version). If any attempt succeeds, `onSucceed` fires → `setPhase("protected")` → the full happy path continues, completely undegraded. The former Hybrid-only 15s "Still connecting…" safety net (`useHybridReveal`'s dead `showConnectHelp`, which could never fire while connect was a fixed ~3.2s) was retired — it would have conflicted with this new, synchronized mechanism now that connecting can genuinely run long during a simulated failure.

**Tier 2 — calm, cause-specific failure screen** (`components/ConnectionFailedOverlay.tsx`), shown once Tier 1 exhausts (`onTier1Exhausted` → `phase = "failed"`) or immediately for a user-required cause. Deliberately reuses NONE of the danger styling: a new `visualPhase` (`phase === "failed" ? "connecting" : phase`) is threaded to every version instead of the raw phase, so the map/pin/gradient/chip/activity-cards freeze at their neutral "connecting" visual — no re-scrambling, no fake progress, no red. Cause-specific header icons in calm gray (`#8882A0`): `WifiOff` (lucide) for `no-internet`, `PadlockNeutral` (`components/Padlocks.tsx`) for all other causes. Copy (`CONNECTION_FAILURE_COPY`, `lib/connectionFailureConfig.ts`) uses "yet" framing throughout ("We couldn't connect you yet"), never "Connection failed"/"Something went wrong"; the one inferential cause (`network-blocks-vpn`) hedges ("This network **may be** blocking VPN connections"). One primary action (cause-specific "Try again") plus an always-present, never-gated secondary "Go to the app". The one allowed user retry (`retryConnectAttempt`) reruns the same attempt sequence; success rejoins the happy path exactly like Tier 1; failure (`onTier2RetryFailed`) exits automatically to Tier 3 — no second failure screen.

**Tier 3 — graceful exit to the app.** Reached via "Go to the app" (any point on the failure screen) or the Tier 2 retry's failure. Calls `onExit([], "free", { vpnConnected: false, deferredDueToConnectionFailure: true })` — a new flag on `OnboardingExitOptions` (`lib/sessionPlan.ts`) distinct from a deliberate `vpnConnected: false` skip (e.g. JTBD "Go to app directly"). **Never the upsell** — this exit skips straight past `jtbd`/`tuned`/`upsell`/etc. entirely, the same way every other disconnected-skip exit already does. In `App.tsx`, `handleEnterApp` reading `deferredDueToConnectionFailure` sets `deferredOnboarding` (persisted to `localStorage` under `onboardingDeferredDueToFailure` — this prototype has no account/session to key off instead) and suppresses the "Set it up your way" modal + the "You're all set" welcome banner (via the existing `suppressWelcomeBannerRef`) and the Profiles banner (already gated on `onboardingJtbds.length > 0`, which stays `[]` on this path) and confetti (only ever fires inside `PlusWelcomeState`, never reached). **Onboarding is marked resumable, not completed** — no completion flag is ever set for this exit.

**The Tier 3 landing** (`components/DeferredOnboardingBanner.tsx`, rendered by `WorldMap.tsx` in the same slot as `WelcomeBanner`, mutually exclusive with it) is a dismissible banner with two modes, computed in `App.tsx` as `deferredBannerMode`:
- `"retry"` (still disconnected) — *"We couldn't connect earlier. Try again?"* + **Try again**, which calls the exact same `handleConnect` the free-tier connection card itself uses (this is genuinely just "try connecting again").
- `"resume"` (the user connected later, on their own, personalization still unfinished — detected via a `useEffect` watching `vpnStatus` flip to `"protected"` while `deferredOnboarding` is true, which also fires the one-time `connection_deferred_connected_later` analytics event) — *"Want to finish personalizing your VPN?"* + **Continue**, the minimal re-run entry point: `handleDeferredResume` remounts `OnboardingV2` with a new `resumeAtJtbd` prop, which opens `phase` directly on `"jtbd"` (skipping stage 1 entirely, since the user is already connected) instead of `"unprotected"`. Completing that resumed flow calls `handleEnterApp` again without the deferred flag, which clears `deferredOnboarding` and fires `connection_deferred_onboarding_completed` — the upsell/checkout flow IS reachable from a resumed session (the connection succeeded; this is just finishing setup, not the failure path anymore).

Dismissing the banner (`X`) only hides it for the current situation; it reappears if the situation changes (e.g. dismissing "retry" then connecting later still shows "resume").

**Analytics** (`lib/analytics.ts` → `trackConnectionFailureEvent`, same console-only convention as `trackUpsellEvent`/`trackTuningEvent`): `connection_attempt_start`, `connection_resolved` (cause, which attempt resolved it, attempt count), `connection_tier1_exhausted`, `connection_tier2_view`, `connection_tier2_retry`, `connection_tier2_exit` (which exit: `"go_to_app"` vs `"auto_after_retry_fail"`), `connection_deferred_connected_later`, `connection_deferred_onboarding_completed` — covering every field the task asked for (cause, tier, remedy, attempts, retry, exit, later connection, deferred completion).

**Reduced motion / accessibility:** `ConnectingNarration`'s text swaps are unanimated by construction; `ConnectionFailedOverlay` uses a plain fade when `useReducedMotion()` is true. The failure screen is `role="alertdialog"` with `aria-labelledby`/`aria-describedby`, both actions are native, keyboard-focusable `<button>`s, and narration lines are `aria-live="polite"`.

## States / Key User Flows

`Unprotected → Connecting → Protected → JTBD Selection → Tuning → Tuned Result → VPN Plus Upsell → [Simulated Web Checkout → Checkout Loader → VPN Plus Welcome] → App transition → "Make Proton VPN yours" modal`

1. **Unprotected** — Dark map centered on the user's real location. Coral open-padlock header, danger headline, ISP warning. Red pulsating pin framed by an animated sci-fi targeting reticle (`TargetingReticle`). Glassmorphic info card (3 rows: country+flag, IP, ISP). CTA: "Protect my online identity".
2. **Connecting** — Spinner header, "Protecting your online activity....". Background gradient morphs coral → slate. Reticle fades out, pin turns gray, map slowly zooms out. Card values progressively redact to asterisks (labels stay readable). VPN connect is simulated (min 3.2s on the happy path). If a failure is being simulated (prototype HUD only — see "Connection failure path" below), the headline is replaced by plain-language narration ("Trying a different location…", then "Trying a different way to connect…") while silent auto-remedies run; exhausting them shows a calm Tier 2 failure screen instead of advancing to Protected.
3. **Protected** — Teal closed-padlock header, "...now fully protected!". Gradient morphs slate → teal. Map flies to the VPN server (Netherlands). Teal pulsating pin wrapped in an animated protective shield aura (`ShieldAura`). Info card rebuilds to 4 staggered rows (location hidden, appears-in country+flag, IP hidden, VPN IP in teal). CTA: "Continue".
4. **JTBD Selection** (`JtbdGridPanel`) — a centered 3×2 grid of 6 selectable JTBD tiles (icon + label), a small contextual "wink" line + idea-bubble illustration once a tile is picked, and a dynamic Continue ("Continue" → "Tune for {jtbd}" once selected) + top-right **"Go to app directly"** (chevron, exits to main app **disconnected** — `onExit([], "free", { vpnConnected: false })`). Picking a tile again deselects it. Continue advances straight to `tuned` (no separate loader — see below); **Go to app directly** exits.
5–6. **Tuned Result** (`TunedResult`, phase `tuned`) — a single, consolidated result step with no separate loader: opens with its own centered intro (see "Header intro/move/counter" below) that becomes the result header, then the 4 settings materialize one at a time into the selected **layout** (Stacked / Split by Status / Card Grid / Compact List — see "Tuning-stage layouts" below), then completes with a "Tuned for {jtbd}" title, a derived summary subtext, and Continue. **No tip** anywhere on this screen (removed across all 4 layouts). Top-left Back button returns to JTBD selection. Plus users (`userPlan="plus"`) see all 4 items as applied (no locked items, no tier-boundary widget).
7. **VPN Plus Upsell** — Split-screen conversion screen. "Get VPN Plus" → simulated web checkout (below); "Continue free" → exit.
7.5. **Simulated Web Checkout** (`web-checkout`, `SimulatedWebCheckout`) — a fake Chrome browser window opens on top of the (still-mounted, dimmed, inert) upsell screen, containing a prototype "Review subscription and pay" page. See "Simulated web checkout" below for the full breakdown. Happy path only — no cancel/close/abandon handling; window controls are decorative. Ends with the user clicking the dimmed app behind (only live post-payment-success), which advances to the Checkout Loader.
8. **Checkout Loader** — Transparent overlay reusing `LoaderScreen` (same teal gradient background), UNCHANGED. Title "Completing checkout...", subtitle "Confirming your payment. This takes a few seconds." 3000ms fixed timer (no real API), then advances to Plus Welcome.
9. **VPN Plus Welcome** (`PlusWelcomeState`) — Celebrates the upgrade. **Prototype default: "Profiles showcase"** (`layout="profiles-showcase"`) — unlocked profile cards in a centred autoplay carousel (`ProfilesShowcaseWelcome`). The four settings-list layouts (Minimal list / Richer list / Split view / Card Grid) remain selectable via the stage-3 **Layout** dropdown; those reuse stage 2's four layout renderers with the locked→unlocked paid-item animation (see "Stage 3 reuses stage 2's layouts" below). Confetti fires once — default coloured shapes for most JTBDs; when **Streaming** is among the selected intents, the burst is popcorn emoji (`🍿`) instead. Continue ("Start using VPN Plus") fires `onEnterApp`.

**The upsell screen** (`VPNPlusUpsell`, the **default** of 10 selectable upsell versions — see "Upsell alternative layouts" and "Combined profiles + features upsell" below). Left (~52%): "What VPN Plus unlocks for you" heading, JTBD-personalized subheading, 3 JTBD-specific benefit cards (green check + outcome + "via {feature}" + (i) tooltip), an italic "everything else" line, a factual trust-signal row, and two CTAs. Pricing is folded into the primary CTA: "Get VPN Plus" with a concise second line ("$4.99/mo, billed yearly · save 50%"); the secondary ghost "Continue free" stays clearly available. Right (~48%): black panel with the 3D ▽+ hero image bleeding to the edges. A top-left Back button returns to the Tuned Result. Content density is tuned to fit the 768px window without scrolling. Uses Tailwind container queries (`@container`): below ~900px panel width the hero is hidden and content goes single-column. "Continue free" still exits directly; **"Get VPN Plus" now opens the simulated web checkout** (`web-checkout` phase) instead of going straight to the checkout loader. Lucide icons (Info, ArrowUpRight, ShieldCheck, BadgeCheck, RefreshCw); Radix Tooltip on (i) icons. This component is left **byte-for-byte untouched** by the 5 alternatives below — it stays the reference implementation the shared hook mirrors.

### Upsell alternative layouts (`versions/upsell/`)

5 alternative layouts for the "Upgrade to Plus" upsell screen, each replicating a distinct, real-world paywall/upsell pattern researched on Mobbin, built alongside (never replacing) the original `VPNPlusUpsell`. All 10 upsell versions (these 5, the original split-hero default, and the 4 combined profiles + features layouts documented in the next section) are selectable via a new **"Upsell"** dropdown in the prototype-controls HUD (shown whenever the "Upgrade to Plus" stage is active) — a `UpsellVariant` (`"default" | "comparison-table" | "value-stack" | "card-grid" | "plan-selector" | "hero-spotlight" | "profiles-hero-tabs" | "profiles-band" | "profiles-paired" | "profiles-fan"`) state lifted to `App.tsx`, threaded through `OnboardingV2`'s `upsellVariant` prop to a render switch inside the existing `phase === "upsell"` block, mirroring how `resultLayout` already drives `TunedResult`/`PlusWelcomeState` — but this is a genuinely SEPARATE selector/state, since `resultLayout` only affects the Plus Welcome step, never the upsell screen itself. **`profiles-fan` ("Profiles + features — Fanned deck") is the prototype default** — `App.tsx` initialises `upsellVariant` to it, and it sits first in `UPSELL_VERSIONS`. `SimulatedWebCheckout` also receives `upsellVariant` and renders the matching dimmed layout behind the fake browser, so the backdrop always matches whichever screen the user actually clicked "Get VPN Plus" from.

**Non-negotiable across all 10 (including the default):** every alternative is populated from the EXACT same intent-driven engine, never new/invented content —

- **Content resolution** — `versions/upsell/useUpsellContent.ts`, a hook mirroring `VPNPlusUpsell.tsx`'s own inline resolution byte-for-byte: single mode → `JTBD_UPSELL[jtbdKey].benefits` (3 hand-curated cards) + `JTBD_TUNING_RESULT[jtbdKey]`'s own `enabled`/`paid` arrays; Multiple mode (2+ picks) → the SAME `mergePaidFeatures` → `rankPaidFeatures` → `capList(., UPSELL_MULTIPLE_HIGHLIGHT_CAP)` pipeline the default screen already uses for its highlighted benefits, plus (for the comparison table's Free column) `mergeFreeSettings` → `rankFreeSettings` → `capList(., TUNED_RESULT_TIMING.freeRowCap)` — the SAME cap the Tuned Result screen already uses for that list. No new ranking, no new caps beyond ones already established elsewhere in this codebase.
- **Subtitle** — `versions/upsell/lib/UpsellSubtitle.tsx` renders the identical "Based on your **{jtbdWord}** pick, here is what VPN Plus turns on." (single) / `upsellSubtitleMultiple(count)`'s "Based on your {count} picks…" (multi) sentence every layout shows verbatim; only its wrapping element/size differs per layout (e.g. Hero Spotlight shows it as a small supporting caption above its own top-benefit headline, rather than the dominant title).
- **Pricing** — always `UPSELL_PRICING` (`jtbdUpsell.ts`), never invented; the plan-selector's monthly anchor and the value-stack's per-day framing are just different PRESENTATIONS of the same 2 real numbers ($4.99/mo billed yearly, $9.99/mo monthly).
- **CTAs** — `versions/upsell/lib/UpsellCtaBlock.tsx` renders the same "Get VPN Plus" (+ optional pricing subline)/"Continue free" pair, calling the SAME `onUpgrade`/`onContinueFree` props every layout receives (→ `web-checkout` phase / `handleExit(..., "free")`, both unchanged). The plan-selector's monthly/annual toggle is cosmetic only — either selection still calls the same `onUpgrade`, since the checkout flow/amounts are out of scope.
- **Assets** — every layout reuses EXISTING assets only: `checkmark-circle-filled.svg`/`vpn-plus-badge.svg` (comparison table's Free/Plus cells, reused from `EnabledFeatureRow`/`PaidFeatureRow`'s own locked/unlocked convention), the 7 streaming-service logos (`StreamingLogos.tsx`, shown whenever Streaming is part of the selection, same gate as the default), the real trust-signal SVGs (`usp-open-source`/`usp-swiss-based`/`usp-no-logs`, used by the value-stack — the default screen imports these but never renders them), each Plus feature's own decorative icon (`PaidFeature.asset`), the shared `upsell-sparkle.svg` placeholder (single mode's 3rd hand-curated benefit, which has no matching tuning-result icon — same fallback the default uses for every benefit), and the existing 3D `upsell-hero.jpg` (Hero Spotlight, resized/cropped rather than full-bleed). No new artwork.
- **Honesty** — no fabricated stats, testimonials, or user counts anywhere; a social-proof-led pattern was deliberately excluded from the 5 during research since it could not be populated with real, sourced numbers.

**The 5 layouts** (`versions/upsell/*.tsx`, each a `UpsellVersionProps` implementation — `jtbdKey`/`selectionMode`/`selectedJtbds`/`onUpgrade`/`onContinueFree`/`onBack`, matching `VPNPlusUpsellProps`):

1. **Feature comparison table** (`ComparisonTable.tsx`) — a single centered column: headline/subtitle, then a bordered Free-vs-Plus table (Duolingo/Brilliant/Monzo pattern) — every free setting checked on both columns, every paid feature locked (▽+ badge) on Free / checked on Plus — everything-else line, CTAs.

4. **Plan-selector toggle** (`PlanSelector.tsx`) — foregrounds the pricing decision itself: two selectable price cards (Annual — real $4.99/mo + save 50% badge — vs Monthly — real $9.99/mo anchor) above a compact benefit checklist (Public/Bevel/ChatGPT pattern).
5. **Single hero-benefit spotlight** (`HeroSpotlight.tsx`) — unlike every other layout (2-3 benefits with equal billing), leads with ONE dominant benefit — the top-ranked feature for the selection — as a large hero (existing 3D art + that feature's own icon) with its own outcome sentence as the headline; the remaining benefits appear as a smaller "Plus, also unlocked" list below (MyFitnessPal/Duolingo-MAX/Cleo pattern).

**Shared plumbing** (`versions/upsell/lib/`, `versions/upsell/types.ts`, `versions/upsell/timing.ts`) — `UpsellBackButton`/`UpsellCtaBlock` (both fire analytics before calling through), `UpsellSubtitle`, `InfoTooltip`, `StreamingLogos` (all lifted/adapted from `VPNPlusUpsell.tsx` so the 5 layouts never duplicate that logic 5 times), and `useTrackUpsellView` (fires `upsell_view` once per mount). New structural-only copy (column headers, section headings, plan-card labels — never pricing/benefit content) lives in `lib/upsellVersionsCopy.ts`, matching this codebase's existing centralized-copy convention (no i18n framework).

**Analytics** (`lib/analytics.ts`, net-new — no analytics infrastructure existed anywhere in this repo before): a minimal `trackUpsellEvent(event, payload)` util that `console.info`s (swappable for a real provider later without touching call sites). Fires `upsell_view` (on mount, every layout including the default's own dimmed re-mount inside `SimulatedWebCheckout`), `upsell_get_plus`/`upsell_continue_free` (from `UpsellCtaBlock`), and `upsell_back` (from `UpsellBackButton`) — every payload is tagged with the active layout's `version` id (e.g. `"comparison-table"`) plus `jtbdKey`/`selectionMode`/`selectionCount`, so funnel comparisons across all 10 layouts are directly comparable. The original `VPNPlusUpsell` is NOT instrumented (left untouched); only the 9 alternative layouts fire these events today.

**Reduced motion:** all 9 alternatives read `useReducedMotion()` (`versions/lib/useReducedMotion.ts`) and skip their entrance stagger entirely when active (root `initial`/`animate` become `undefined` instead of the `"hidden"`/`"show"` variant labels, so content renders in its final resting state immediately) — a step beyond the default `VPNPlusUpsell`, which does not itself check this.

### Combined profiles + features upsell (`versions/upsell/Profiles*.tsx`)

4 further upsell versions, each combining the ranked Plus-feature list every version above already shows with the **profile cards from the tuning screen's "Profiles carousel v2"** — the concrete, named, per-intent profiles a Free user was just shown and can't have. They obey every "non-negotiable" rule listed above: same `useUpsellContent` engine, same `UpsellSubtitle` sentence, same `UPSELL_PRICING`, same `UpsellCtaBlock`/`UpsellBackButton`, existing assets only, no fabricated claims. Since a Plus run skips the upsell phase entirely, all 4 are Free-facing by construction and carry no plan branching.

**Two render switches, not one.** Adding an upsell version means registering it in `OnboardingV2.tsx`'s `phase === "upsell"` block *and* in `SimulatedWebCheckout.tsx`'s dimmed-backdrop block, which duplicates the same switch with `noop` handlers. Miss the second and the layout still works, but clicking "Get VPN Plus" opens the fake browser over an empty backdrop instead of the screen the user just came from — a silent gap, since neither switch has a fallback branch. All 4 are registered in both.

**The one design problem these four differ on.** The feature rows and the cards' settings chips are partly the same data seen twice: a Downloading card's chips read "P2P server · Port forwarding · NetShield", and one of the ranked feature rows reads "Connect to servers set up for file-sharing / via P2P servers". Combining the two naively sells the same thing twice in two registers. The chips are the lever, and each layout takes a different position:

| Version (`UpsellVariant`) | Component | Arrangement | Position on the overlap |
|---|---|---|---|
| `profiles-hero-tabs` | `ProfilesHeroTabs.tsx` | One profile at `UPSELL_CARD_TALL_H` (400) as the dominant object + a tab strip, features in bordered `"card"` rows beside it | Separate columns, so nothing competes for the same vertical run — chips stay on, features keep full billing |
| `profiles-band` | `ProfilesBand.tsx` | Full-width `CarouselTrack` band of 220px cards under the headline, features as compact `"line"` rows beneath an "Unlock all N" boundary | **Chips off.** The only layout where cards and features stack in one vertical run, so the cards carry artwork/name/lock and the list below carries every settings claim exactly once |
| `profiles-paired` | `ProfilesPaired.tsx` | One row per profile: a 108×80 `UpsellProfileThumb` beside the feature(s) that profile caused, chips on the row | **Eliminated** — each fact is stated once, as a personalized artifact and a capability claim in the same row |
| `profiles-fan` | `ProfilesFan.tsx` | The default screen's left column, minus its subtitle, its benefit rows' borders, and each benefit's `via {featureName}` subline, plus a `UpsellHeroMark` above the headline; the right 48% swaps the 3D render for the profiles as a dot-paged, auto-advancing `AutoplayCarousel` with an intro line above it | Ignored by design — separate columns, and a card corroborating a claim beside it isn't a card repeating a claim beneath it |

**Full-strength cards with an additive lock, and why (`profiles/UpsellProfileCard.tsx`).** The tuning screen's `FreeProfileCard` dims a locked profile to 45%, because that screen is stating a fact ("not yours"). This screen's job is the opposite — make the same object desirable enough to pay for — and a faded card sells nothing. So the dimming is replaced by two independent *additive* signals: a Plus-violet inset rim + outer glow, and the `vpn-plus-mark.svg` badge in the top-right corner (no lock glyph beside the name — confirmed at checkpoint). Two rather than one specifically because the failure mode in the other direction is real: a full-strength card with no Plus signal reads as **already owned**, and nobody pays for what they think they have. `UpsellProfileCard` is deliberately a separate component rather than a `variant` prop on `FreeProfileCard` — the two disagree on the card's entire meaning — but everything factual is shared (same `PROFILE_CARD_PHOTO` artwork at the same width, same `ProfileIconTile`, same name, same derived `profileChips`). **Hover/focus disclosure** now matches the Plus tuning carousel v2 card: chips crossfade to three checked benefit lines from `PROFILE_BENEFITS` plus the per-profile `hoverSubtitle`, with a deepening scrim and a slight artwork zoom — opens on focus as well as hover so keyboard users aren't locked out. Layouts that hide chips (`showChips={false}`, e.g. `profiles-band`) still get the benefit list on hover; the default face is just quieter. Same `sr-only` `PLUS_AVAILABILITY_LABEL` line, so it's recognisably the same card, not a second design.

**The pairing is causal, not positional (`profiles/useUpsellProfiles.ts`).** `profiles-paired` needs to know WHICH pick put each feature on the list, and `useUpsellContent`'s `benefits` have already flattened that away. So this hook re-runs the *same* shared `mergePaidFeatures → rankPaidFeatures → capList(., UPSELL_MULTIPLE_HIGHLIGHT_CAP)` pipeline (no second ranking, no new cap) and defers the flattening, keeping `MergedPaidFeature.primarySourceJtbd`. Pairing by array index instead would caption the Gaming card with a file-sharing benefit the moment the two lists ordered differently. Single mode needs none of it: one profile, so all 3 hand-curated `JTBD_UPSELL` benefits belong to it by construction.

**A profile can honestly have no feature.** Each intent contributes 2 paid features, the union dedupes by name, and the displayed list caps at 3 — so a 6-pick run has 6 profiles and 3 features, and 3 profiles legitimately pair with nothing. They are neither hidden nor given a filler benefit: `profiles-paired` puts them in a trailing thumbnail strip with `pairedMore(n)` ("And 3 more profiles, ready to unlock"). A profile with *two* displayed features stacks both in its one row, so rows and profiles stay one-to-one either way. `orphanBenefits` is a defensive list for a feature whose contributor isn't on screen — unreachable with today's data, but a screen that could silently drop a feature it was told to show needed the floor stated in code.

**Selection-count scaling** is where these four differ most in robustness: `profiles-hero-tabs` is flat in both directions (1 pick hides the tab strip; 6 adds tabs), `profiles-band` reuses `CarouselTrack`'s existing "grow arrows and edge fades only when actually overflowing" behaviour but is thin at 1 pick, `profiles-fan`'s `AutoplayCarousel` shows dots regardless of count (they're hidden entirely at 1) so it scales identically at every count, and `profiles-paired` is the one that can need a scroll at 6 picks with Streaming selected (its container is `overflow-y-auto`, same as every other version).

**`profiles-fan` went through several revisions after being seen rendered**, all on direct request, and ended up the most changed of the four from its original sketch:

- Its left column dropped the "Based on your N picks…" subtitle (redundant once the deck on the right is doing the personalization work) and each benefit row's border/fill/padding and `via {featureName}` subline (`UpsellBenefitRow`'s `bordered={false}` and `showFeatureName={false}`) — three bordered boxes underneath the 3D mark and headline read as a fourth competing block rather than a supporting list. Rows use the shared **sparkle icon** (`useSparkleIcon`) rather than each feature's own decorative asset — the same `upsell-sparkle.svg` `VPNPlusUpsell` already uses — so the list reads as one unified "things Plus unlocks" block rather than six product icons competing with the JTBD badges on the profile deck. The rows sit **20px apart** rather than the other layouts' 8px, since with the border gone spacing is the only thing left separating one claim from the next — 8px let three distinct benefits read as one loose block. The list block carries **`my-[18px]`** on top of the column's 18px gap, doubling the space above the list (icon row → first feature) and below it (last feature → "everything else") without inflating every other sibling.
- `UpsellHeroMark` above the headline grew twice — 56px → 112px → **150px** — after feedback each time that the previous size read as too small to register as the product itself.
- A `deckIntro(n)` line ("You'll also be able to use these N personalized profiles, built around what you do online") sits above the profiles, stating the group IS an unlock rather than leaving it to read as decoration.
- **The right panel was rebuilt twice, then its cards grew twice more.** The original sketch cascaded the profiles downward as an overlapping deck (a `stepFor()` helper traded overlap for how much of a partly-hidden card stayed readable). That became a plain horizontal `CarouselTrack` row, the same component `profiles-band` uses. It's now `AutoplayCarousel` (`profiles/AutoplayCarousel.tsx`) instead — a distinct primitive, not a `CarouselTrack` configuration: `CarouselTrack` is for a row that MIGHT overflow and should show no chrome when it doesn't; `AutoplayCarousel` is for a row that always wants to be read as "N things, here's where you are" — page dots (a longer pill for the active one), a fixed 4-second auto-advance, and a standing right-edge fade — regardless of whether everything already fits. Requiring `CarouselTrack` to grow dots, autoplay and a one-sided fade behind extra props would have made `profiles-band` pay for behaviour only this layout wants. Card height went 260 → 320 → **`UPSELL_CARD_TALL_H` (400)** — the same height `profiles-hero-tabs` gives its single dominant card — each earlier number reading too short once seen next to the now-taller, unbordered left column; there's no other element sharing this panel to stay proportionate to, so it can reuse the tallest card size that already exists rather than inventing a fourth number.

`AutoplayCarousel`'s index is derived from scroll position, not just tracked as state: clicking a dot sets it immediately (so the dot highlights without waiting for the smooth-scroll it triggers to finish) and scrolling the track independently recomputes the same index from `scrollLeft` on every `onScroll` — so a manual drag updates the dots correctly despite never calling the click handler. Auto-advance is a `setTimeout` re-armed on every index change (whether that change came from the timer, a click, or a drag), which gives "an interaction always buys a fresh interval" for free, with no separate "user just interacted" flag to keep in sync. It is suspended entirely under reduced motion — an unrequested screen change on a fixed timer is exactly what that preference opts out of — while dots and dragging still work.

**The right-edge fade is deliberately one-directional** (`rightEdgeFade`, on by default, off automatically whenever dots are — i.e. at exactly 1 profile). Unlike `CarouselTrack`'s two-sided mask, which fades whichever edge currently has more content scrolled past it, this fade never appears on the left. The carousel loops forward via autoplay rather than exposing a "scrolled past the start" state, so item 0 is always a real, fully-visible start — there's never a moment where fading the left edge would be telling the truth. The right fade is a standing "there's more" cue tied to the carousel's existence, not a response to a specific scroll offset.

**The deck sits with a fixed left inset, not flush against the panel edge.** `AutoplayCarousel`'s `LEFT_INSET` (24px) adds extra left padding to the track on top of the glow clearance below, deliberately left UNCANCELLED by the matching negative margin (which only cancels the glow padding on all four sides otherwise) — so it renders as a real, constant gap, shifting every card right by the same amount regardless of which one is active. Unlike `CarouselTrack`'s own two-sided fade, this carousel never had a left mask (see `rightEdgeFade`'s note on why its own fade is one-directional) — with the panel-edge glow fix landing, a card sitting flush against the panel's edge (most visible at rest, on the first card) had nothing softening it, and a real gap reads better here than adding a left fade would, since this carousel's start is always genuine, never a "scrolled past" state a fade should be honest about.

**Fixed: the card's own glow was being clipped by its scroll container.** Both `AutoplayCarousel` (here) and `CarouselTrack` (`profiles-band`) scroll horizontally via `overflow-x-auto`, but per the CSS overflow spec, setting `overflow-x` to anything but `visible` forces `overflow-y` to compute to `auto` too when it's left `visible` — so each track was ALSO clipping `UpsellProfileCard`'s outer `box-shadow` glow above and below every card (and, at the scroll extremes, to the left/right of the first/last card), invisibly, since neither track ever intended vertical clipping. Both now wrap their scrollable element in a plain (non-flex) block carrying `GLOW_PAD_X`/`GLOW_PAD_TOP`/`GLOW_PAD_BOTTOM` (32/24/44px — sized to the glow's largest layer, `0 10px 30px`) as padding, with a matching negative margin on the wrapping block that cancels it back out. A plain block's `auto` width resolves via the standard box-model equation against its containing block (`width = containing width − margins`), which is what lets the padded, negative-margined box bleed symmetrically past the track's nominal bounds instead of just shifting position — the same trick would silently break inside a flex item under `align-items: center` (its `auto` cross size resolves via `fit-content`, not that equation), which is why both fixes deliberately nest a plain block between the scroll element and its non-flex `relative w-full` wrapper rather than applying the padding/margin directly to a flex child. Harmless on `CarouselTrack`'s other callers (the tuning carousels), whose bordered cards have no shadow to reveal.

**The 3D hero art is kept, demoted** (`profiles/UpsellHeroMark.tsx`) — a compact crop of `upsell-hero.jpg`, centred above the headline on `profiles-band` (136px) and `profiles-fan` (150px) and beside the header row on `profiles-paired` (120px). It is deliberately **absent** from `profiles-hero-tabs` (the tall card is already that layout's hero; two competing heroes on one screen). Height is derived from width at `RATIO = 0.47` so the portrait source is never cropped to a sliver. Distinct from the flat VPN Plus badge on profile cards — `vpn-plus-mark.svg` at 39×24 (1.5× native), placed directly in the top-right corner of `UpsellProfileCard` (and `FreeProfileCard` on the tuning screen) with no extra chip wrapper, replacing the older bloated `vpn-plus-badge.svg` export.

**Why not a full-width strip of `upsell-hero.jpg`**, since the first attempt was the latter: that raster is **661×1024 — portrait**, sized for the default upsell's own ~490×768 right-hand panel. Under `object-cover`, a box `W` wide scales the source to `1.549 × W` tall, so the visible slice is `H / (1.549 × W)` of the image — and the ▽+ badge occupies roughly the middle third. A 720×60 strip therefore shows about 5% of the height: a featureless dark band. `UpsellHeroMark` derives its height from `width` at `RATIO = 0.47` (~a third of the image in frame) rather than taking a `height` prop.

**Shared pieces** live in `versions/upsell/profiles/`: `UpsellProfileCard.tsx` (+ `UPSELL_CARD_W`/`UPSELL_CARD_H`/`UPSELL_CARD_TALL_H`), `UpsellProfileThumb.tsx`, `UpsellHeroMark.tsx`, `AutoplayCarousel.tsx` (used only by `profiles-fan`; a generic `<T>` dot-paged/auto-advancing carousel with an optional one-sided `rightEdgeFade`, not coupled to profiles specifically), `UpsellBenefitRow.tsx` (the default's bordered benefit card as `"card"`, a `bordered={false}` option that drops the border/fill/padding, a `showFeatureName={false}` option that drops the `via` subline outright rather than relocating it, and a `useSparkleIcon` option that swaps each feature's own asset for the shared `upsell-sparkle.svg` — the latter three used only by `profiles-fan` — plus a compact `"line"` register that moves the feature name into the tooltip for the layouts where the cards already own the visual weight), and `useUpsellProfiles.ts`. `ProfilesBand` reuses `tuned-result/concepts/profiles-carousel/CarouselTrack.tsx` unchanged, passing its optional `label`; that cross-module import direction already exists in reverse (`CarouselCardV2` imports `versions/upsell/lib/InfoTooltip` and `StreamingLogos`). Copy is one shared `UPSELL_VERSIONS_COPY.profilesCombined` block rather than four — these layouts differ in arrangement, not in what the screen claims, and four copies of one heading is how they'd drift on wording nobody meant to change. Its `groupLabel` is "Profiles available with VPN Plus", not the tuning carousel's possessive "Your personalized profiles", which is the one claim this screen can't make.

### Simulated web checkout (`web-checkout` phase)

Inserted between the upsell CTA and the existing checkout loader, simulating "leaving the app to pay on the web" without a real payment backend (happy path only — no cancel/close/abandon handling; see Forbidden Actions in the originating task).

**Why built fresh, not embedded from a reference source:** a real Proton checkout page was inspected as a potential reuse source, but it turned out to contain only the Chargebee/Stripe/hCaptcha payment-processor iframe plumbing (hosted card-number/expiry/CVC iframes, a bot-challenge widget, a cross-origin fraud-detection bridge) — no visual "Review subscription and pay" page (no plan cards, no Summary panel, no totals/tax math) exists in that source to reuse, and the iframes that are there only function against a live backend. `CheckoutPage.tsx` is therefore a new prototype component, matching a provided screenshot's copy/layout/numbers exactly rather than reusing that source.

- **`SimulatedWebCheckout.tsx`** (`components/checkout/`) — orchestrator. Renders the upsell screen again as the dimmed, `aria-hidden`, fully inert "app behind" (never unmounted, per Scope Lock), a full-bleed overlay `<button>` that doubles as the dimming layer AND the "click to return" target (disabled — cursor-default, darker dim — until payment succeeds; live — cursor-pointer, lighter dim, plus a fading-in "Click on the VPN app window to continue" hint — once it does), and the browser window on top. Its root is an isolated stacking context: the backdrop wrapper is explicitly `z-0` (confining `VPNPlusUpsell`'s own internal `z-[1000]`), the dim/return layer is `z-10`, browser `z-20`, and post-success hint `z-30`. This explicit layering prevents the reused upsell from painting over and hiding the fake browser. Owns `processing`/`success`/`returning` state and the two timers (pay→success, return-click→exit) — both centralized in `checkoutTiming.ts`.
- **`BrowserWindowChrome.tsx`** — the Chrome-style shell: one-tab tab bar (Proton VPN favicon from `assets/proton-vpn-logo.png` + "Proton VPN — Review subscription"), address bar (padlock + simulated `account.proton.me/vpn/checkout` URL), decorative minimize/maximize/close controls. All browser-view copy uses **Inter** (loaded via `fonts.css`). Sized to 88%×88% via `inset-[6%]`, so the dimmed app is visible around every edge. This inset-based positioning deliberately avoids translate-based centering: Framer Motion owns the element's `transform` for its scale animation, so combining scale with Tailwind `translate(-50%)` could overwrite the centering transform. Scale 0.96→1 + fade entrance/exit (~250ms each way); `prefers-reduced-motion` (`useReducedMotion`) drops the scale for a plain fade.
- **`CheckoutPage.tsx`** — the embedded "Review subscription and pay" content: 3 selectable subscription-option cards (24/12/1-month, `lib/checkoutPlans.ts`), 4 selectable payment methods (only Credit/debit card reveals card fields; no validation on any field), a Summary panel (plan badge/term, per-month rate, total, credits, amount due, "Pay US$X now", tax note, expandable "What do I get?"). Selecting a plan re-renders the whole Summary from `checkoutPlans.ts`.
- **`CheckoutSuccess.tsx`** — replaces the checkout content once "Pay" resolves: check mark, "Payment successful", "You're all set — return to the Proton VPN app to continue."
- **`lib/checkoutPlans.ts`** — the 3 plans + derivation math, entirely from screenshot facts (24-month: total US$119.76, -50%/"Save US$120", credits -US$1, amount due US$118.76, "Including 21% tax: US$20.78", renews after the term then billed every 12 months at US$83.88; 12-month: US$6.99/mo, "For US$83.88, Save US$36"; 1-month: US$9.99/mo). Everything else is DERIVED, not invented: amount due = total − US$1 credits; tax = total × 0.21/1.21 (VAT-inclusive, verified against the 24-month screenshot figure); the "Save" badge/amount is measured against the US$9.99 anchor monthly rate for the same term. Renewal dates are computed from the real current date + the plan's term (not hardcoded), so they stay correct as time passes.
- **`lib/checkoutCopy.ts`** — every browser-chrome/page/summary/success string, centralized (no i18n framework exists in this codebase — see "Tone of voice" below for the established precedent this follows: strings live in one exported object, not inlined in JSX).
- **`checkoutTiming.ts`** — `CHECKOUT_TIMING`: window entrance/exit (250ms each), page-load spinner (`pageLoadDuration`, 2000ms), pay→processing→success (2000ms), success fade-in (300ms).

**Page load:** the moment the browser window mounts, it shows a plain spinner (a small CSS `animate-spin` ring, not the shared white-stroke `Spinner` component — that one's designed for the dark app background, not this page's light `#f4f5f9` one) for `pageLoadDuration` (2s) before the "Review subscription and pay" content appears — simulating the page actually loading, the same beat a real browser navigation would have. Runs regardless of `prefers-reduced-motion` (`SimulatedWebCheckout.tsx`'s own `pageLoading` state/timer) — this is a simulated page-load delay, not a decorative animation choice.

**Return flow:** clicking "Pay" shows a spinner (reusing `Spinner`) for `payProcessingDuration`, then swaps to `CheckoutSuccess`. Only then does the dimming overlay become clickable; clicking it animates the browser window out (scale/fade) and, after `windowExitDuration`, calls `onReturnToApp` → `OnboardingV2` sets `phase` to the EXISTING `checkout` phase (`LoaderScreen`, unchanged) → `plus-welcome` (unchanged). Pre-success clicks on the dimmed app do nothing (the overlay button is `disabled`).

## Data Model

- **`GeoInfo`** (`lib/useIpDetection.ts`) — live IP detection via `ipwho.is` with a Figma-matching fallback (Lithuania / Orange / 158.6.140.191). Fields: `ip, country, countryCode, city, isp, ispKnown, lat, lng`. `ispKnown` gates connection-stage copy: when true, subtext names the provider as a lead example (`"BT"`) plus "others along the way/in between"; when false (or when `isp === ISP_GENERIC_LABEL`, `"your internet provider"`), copy uses broad phrasing without a concrete name. The real country is captured before connecting and reused for the JTBD panel (the VPN is active by then and would otherwise report the server country).
- **`VPN_SERVER`** (`lib/server.ts`) — fixed "fastest" server (Netherlands / Amsterdam / `146.70.124.18`).
- **JTBD context matrix** (`lib/jtbdData.ts`) — 6 jobs × {UK, US, Germany, France, Netherlands, fallback} factual copy.
- **JTBD wink copy** (`JTBD_WINK_COPY` in `lib/jtbdData.ts`) — one short, knowing line per JTBD, shown by `JtbdGridPanel` next to the idea-bubble illustration once a card is picked. With the user, never at them; no capability-overclaiming; no emoji.
- **JTBD Continue-label copy** (`JTBD_CONTINUE_LABEL` + `JTBD_CONTINUE_LABEL_DEFAULT` in `lib/jtbdData.ts`) — the grid picker's primary CTA text: `JTBD_CONTINUE_LABEL_DEFAULT` ("Continue") pre-selection, one full "Tune for {jtbd}" string per JTBD once picked (not runtime-concatenated, so each locale can adapt word order / the "access" mapping for "Bypass restrictions" naturally).
- **JTBD tuning result** (`lib/jtbdTuningResult.ts`) — per-`JtbdId` tuning outcome (`JTBD_TUNING_RESULT`): `jtbdLabel`, exactly 2 `enabled` features (`outcome`, `settingsName`, `value`, `tooltip`) — always `"Protocol"` then `"Kill Switch"`, the only two free settings this prototype genuinely tunes per-JTBD (confirmed at checkpoint, replacing an earlier illustrative 3-setting-per-JTBD list that included settings never actually wired to JTBD selection) — exactly 2 `paid` features (`outcome`, `featureName`, `asset`, `tooltip`), and a `tip` (string | null). Single source of truth for the Tuning/Tuned screens — no copy is hardcoded in components. Benefit `outcome` sentences use plain, relatable language (no VPN jargon); technical setting/feature names stay unchanged on the right; each row's `tooltip` is a plain-language explanation of that label (shown via an on-demand (i) affordance beside the label). `privacy.tip` is `null`. Protocol resolves to `"Smart"` (downloading, travel, privacy), `"WireGuard UDP"` (gaming, streaming), or `"Stealth"` (bypass); Kill Switch resolves to `"Advanced"` (downloading, privacy, bypass) or `"Standard"` (travel, gaming, streaming) — `PROTOCOL_TOOLTIP`/`KILL_SWITCH_TOOLTIP` keep each value's explanation identical everywhere it appears.
- **JTBD upsell** (`lib/jtbdUpsell.ts`) — per-`JtbdId` upsell content (`JTBD_UPSELL`): `jtbdWord` (subheading injection) + exactly 3 `benefits` (`outcome`, `featureName`, `learnMore`, `tooltip`). Plus `UPSELL_PRICING`, `UPSELL_EVERYTHING_ELSE`, `UPSELL_TRUST_SIGNALS`. Single source of truth for the upsell screen. Pricing/trust values are verified against Proton's public June-2026 pricing/policy (monthly $9.99, 30-day money-back guarantee, Swiss-based, independently audited no-logs); `[UNVERIFIED]` the yearly $4.99/mo is design-confirmed but Proton's current public 1-yr rate is $3.99/mo — confirm region/promo before shipping.
- **Checkout plans** (`lib/checkoutPlans.ts`) — the 3 simulated web-checkout plans (24/12/1-month) + derived Summary math (amount due, VAT-inclusive tax, save amount/percent, renewal date/sentence). See "Simulated web checkout" above for the full derivation.
- **Checkout copy** (`lib/checkoutCopy.ts`) — all simulated web-checkout strings (browser chrome, page, Summary, success).
- **JTBD merge engine** (`lib/jtbdMerge.ts`) — Multiple-mode's data layer. See "Multiple-mode tuning" below for the full writeup.
- **JTBD profile labels** (`JTBD_PROFILE_LABEL` in `lib/jtbdData.ts`) — short capitalized preview label per JTBD ("Streaming", "Access", etc.), used only by the Multiple-mode profile-preview bridge.

### Version Hybrid — combines map-spotlight + browsing experience

`versions/hybrid/` merges the two other groups into one three-act scene (Centered and Split layouts — `hybrid` / `hybrid-split`), reusing as much as possible rather than reimplementing: `Hybrid.tsx` (Centered orchestrator), `HybridSplit.tsx` (Split layout — same content/timing, different arrangement), `useHybridReveal.ts` (the card reveal sequencing shared by both layouts, since it's layout-independent), `LocationChip.tsx` (the one genuinely new visual element, reused by both layouts), `timing.ts` (`HYBRID_TIMING`). Both layouts take the same minimal props shape as v1/v2 (`{ phase, geo, isLive, onProtect, onContinue, tone }`), not `StageOneVersionProps` (they don't need a `BrowsingCopy` object — see "Tone of voice" below for how Hybrid gets its copy instead).

**What's reused, unchanged, and why nothing needed to be imported for it:** `OnboardingMapV2` (map, pulsating pin, `TargetingReticle`, `ShieldAura`, top `StatusGradient`) is rendered **once** by `OnboardingV2`, shared across every stage-1 variant and driven purely by the same `phase`/`geo`/`stage` values `OnboardingV2` already computes generically — Hybrid is simply another transparent overlay on top of it (like v1/v2), so the map/pin/reticle/aura/gradient/flyTo/spinner needed **zero new code**. `ActivityEntry` (from `versions/v4-in-plain-sight/`) is reused for the 3 activity cards — same component and typewriter entrance, with `scrambleText={false}` so Act 2 only transitions the eye + label state (Visible → Hiding… → Hidden) while the card text stays readable; asterisk scrambling is owned solely by `LocationChip`. Card **copy** is Hybrid-specific: `data/hybridActivityEntries.ts` (`HYBRID_ACTIVITY_ENTRIES` — broader category-level lines with Search/Globe/Smartphone icons), separate from v4's narrative `ACTIVITY_ENTRIES`. The real VPN "connect" is the same shared `handleProtect` in `OnboardingV2` every version already calls via `onProtect`.

**What's new:** `LocationChip` — a rounded-pill {flag} {country} · {IP} element. Act 1 shows the real (`useIpDetection`) country/IP, with a skeleton while `!isLive` (mirroring the same loading idiom `InfoCard`/`MaskedValue` use, without reusing that component's row-based markup, which doesn't fit a pill). Act 2 scrambles the country name and IP to asterisks via `useScramble` (200ms after connecting starts, coordinated with the map's flyTo); the flag fades rather than scrambling (nothing to redact in an icon). Act 3 crossfades the pill's *inner content* (not the pill container, which stays mounted throughout) to the resolved VPN identity from `VPN_SERVER` (country/flag/`vpnIp`, IP in teal) — `useScramble` can only mask/unmask its own input text, not resolve to a *different* value, so the value-swap is a straightforward AnimatePresence crossfade of the inner span, the same "persistent container, swapped inner content" idiom used elsewhere in this codebase (e.g. `InPlainSight`'s headline swaps). Also new: `useHybridReveal` (the small local reveal-sequencing state for the 3 cards — `ActivityFeed`, the diary's own orchestrator, hardcodes all 5 entries with no count prop, so it wasn't reusable for "3 cards" as-is — reusing the card component directly and writing new, centralized sequencing for it is the explicitly-scoped-in "new orchestration" piece).

**Split layout (`HybridSplit.tsx`, key `hybrid-split`):** same content, data and `HYBRID_TIMING` pacing as Centered (via the shared `useHybridReveal`), rearranged into a left rail + right panel at an even **50/50 width split** (`w-1/2` each — a deliberate departure from the map-spotlight split's 400px/v2 and the browsing split's 380px rail widths, both narrower-rail conventions) — the left rail holds icon/title/subtext/**activity cards**/CTA vertically centered as one group (the cards sit between the subtext and the CTA, reserving a fixed `min-h-[164px]` — matching Centered's own reservation — so the CTA doesn't drift down as cards reveal progressively), and the right panel holds **only** the location chip, anchored in its **lower half** (the panel is split into two equal flex regions; the top is left empty for the pin, the chip is centered within the bottom one) so it reads as below the pin without needing to measure the pin's exact position. Unlike the browsing split (map-less, opaque), Hybrid's right panel stays **transparent** — the persistent map + pin show through, offset right via `OnboardingV2`'s `splitFocusOffsetX` (256px for the 50/50 rail, vs. v2's 200px for its 400px rail — both simplify to `railWidth / 2`, centering the pin in the remaining region) so the pin lands in that same visible area. No vertical pin *measurement* is attempted in Split (unlike Centered) — matching the map-spotlight split's own precedent, which doesn't center the pin against its rail content either; only Centered needs that, since only there does the pin sit in a dedicated gap between two specific elements.

**Continuity across acts:** the map is never unmounted (owned entirely by the parent, outside Hybrid); the chip is one persistent `motion.div` whose inner content crossfades; the 3 cards are the same `ActivityEntry` instances throughout (`key={entry.id}`, never phase-keyed) — their main text stays readable once revealed, but their `redact`/`sealed` props still drive the eye + label transitions (Visible → Hiding… → Hidden). Icon and title/subtext use `AnimatePresence mode="wait"` keyed by phase for a true overlapping crossfade (a slightly higher-fidelity treatment than v1's own header, which fully remounts `key={phase}` on every transition).

**Opening entrance order (Act 1):** map pin (the shared map's own `ENTRANCE_TIMING.pinAppear`/`bracketsStart`, unchanged) → location chip settles → **beat (~450ms)** → activity cards cascade in (staggered ~175ms) → padlock icon → title → subtext → CTA. Timings live in `HYBRID_TIMING` (`chipEntranceDuration`, `beatAfterChipSettle`, `cardsStart`, `cardStagger`). Reduced motion: same content/order via simple fades, no choreographed beats (minimal 50ms card stagger).

**Pin vertical centering:** the title and subtext slots each reserve a fixed `min-h` (worst-case line count across all three acts' copy) so the block's bottom edge — and therefore the gap available for the map/pin below it — never shifts between acts (previously, hiding the subtext during Act 2, or a headline wrapping differently, would reflow everything below it). `Hybrid` then measures (via `getBoundingClientRect` + a `ResizeObserver`, `useLayoutEffect`) the actual gap between that stable header bottom and the top of the `LocationChip`, and reports the offset needed to center the pin in it through `onPinOffsetChange`, which `OnboardingV2` feeds into `OnboardingMapV2.focusOffsetY`. This is measured, not a hardcoded constant, so it stays correct regardless of exact font metrics or copy length.

**Tone of voice:** Hybrid is fully wired into the same axis as v1/v2/v4/v4-split (see "Tone of voice" below) rather than having its own dedicated, tone-agnostic copy. `CONNECTION_COPY[tone]` gained a third shape, `hybrid` (`HybridCopy`: `exposedHeadline`/`exposedSub`/`connectingHeadline`/`protectedHeadline`/`protectedSub`/`ctaProtect` — the map-spotlight-shaped half of the layout), alongside the existing `mapSpotlight` and `browsing`. The 3 activity cards' `visibleLabel`/`redactingLabel`/`sealedLabel` are **not** duplicated into `hybrid` — Hybrid reads those straight from `browsing` per tone, since the cards are the literal same reused `ActivityEntry` component. Card main-line text comes from `data/hybridActivityEntries.ts` (tone-invariant category copy). `straightforward.hybrid` preserves Hybrid's original headline/sub/CTA verbatim; the other three tones are fresh Hybrid-specific wording in the same voice as their `mapSpotlight` counterparts (not copy-pasted, to avoid two tones showing identical text within Hybrid itself).

**Known gaps, inherited from the source versions (not introduced by Hybrid):** no real connect service and no existing timeout/retry UI pattern exist anywhere in the repo to reuse — the simulated connect is a fixed ~3.2s `setTimeout`, so `HYBRID_TIMING.connectTimeoutMs` (15s) is a defensive hold-with-shimmer safeguard that can't currently fire, with no "Retry" action wired (there's no real failure to retry from). Neither `OnboardingMapV2` nor any existing version has reduced-motion handling for the map/flyTo itself; Hybrid's `prefers-reduced-motion` variant covers everything it controls (chip scramble, card typewriter, icon/title crossfades — via the shared `useReducedMotion`) but inherits the map's un-reduced flyTo, same as v1/v2 do today.

### Plus country selection (Hybrid / Hybrid Split only)

Plus-plan users can pick which country to connect to on the unprotected reveal screen, before protecting themselves — Free's unprotected screen is byte-for-byte unchanged (no dropdown, no reserved space). Scoped to **Hybrid and Hybrid Split only** (confirmed at checkpoint) — the only two connection-stage versions that render an actual flag+country+IP pill (`LocationChip`) alongside the activity cards; v1/v2 show similar data as `InfoCard`/`ControlPanelOverlay` rows instead, and v4/v4-split show none, so neither family gained this control.

**Data foundation.** Real per-country coordinates were previously declared inline inside `components/WorldMap.tsx`; extracted to a lean, dependency-free `lib/countryMarkers.ts` (`countryMarkers: CountryMarker[]`, 93 countries) so onboarding code can reuse the real coordinates without pulling in `WorldMap.tsx`'s heavy module graph (Leaflet + every main-app component it imports) — `WorldMap.tsx` now imports and re-exports the same array, so every existing consumer is unaffected. Flags/ISO codes reuse the existing canonical `getFlagUrl`/`getIsoCode` (`components/flagComponents.tsx`). All three of `countryMarkers`, `flagComponents`'s ISO map, and `CountryBrowser.tsx`'s `allCountries` were verified to contain the exact same 93 country names (cross-referenced at checkpoint) — the picker never curates, shortens, or invents entries.

**"Country selection" sub-toggle (Plus-only, hidden from UI).** The selector is an additive feature ON TOP of Plus, not a defining part of it. The Sign In screen's "With"/"Without" tab group has been **removed from the UI** — only the Plan tabs remain visible — but the option itself is still fully wired: `countrySelectionEnabled` (`App.tsx`) persists to `localStorage` under `"countrySelectionEnabled"` (default **"Without"** / `false`), threads into `OnboardingV2` alongside `plan`, and can still be toggled programmatically (e.g. via devtools). Switching Plan to Plus also resets the stored value to `false`. `showCountrySelect = plan === "plus" && countrySelectionEnabled` is the ACTUAL prop `Hybrid`/`HybridSplit` read (not `plan` directly) for gating the selector + its shared container — `selectedCountry` simply stays `null` ("Fastest country") whenever the toggle is "Without", since the components never render anything to change it.

**`CountrySelect`** (`onboarding-v2/components/CountrySelect.tsx`) — a custom searchable combobox (button + popover), not a native `<select>`, matching `CountryBrowser`'s own search-bar visual language (`rgba(255,255,255,0.05)` fill, `rounded-[4px]`). Options: "Fastest country" (`null`, the default) + all `countryMarkers` names, or — when the optional `ruleOptions` prop is supplied, which only Profiles carousel v2 does — a caller-provided set of namespaced rule entries in place of that single built-in one (see "Profiles carousel v2"). Internally the built-in entry is just the degenerate one-rule case, so both paths run the same code. Options are filtered by a case-insensitive substring match against a search field at the top of the popover. Full keyboard support: click or the trigger opens it; typing filters live; `ArrowUp`/`ArrowDown` move the highlighted row; `Enter` selects it; `Escape` or an outside click closes without changing the value. Selecting a row or pressing `Escape` explicitly returns focus to the trigger button rather than letting it fall wherever the browser decides — both close the popover by unmounting whatever currently holds focus (the option, or the search field), and moving focus first avoids the browser's own, unreliable handling of "focused element removed from the DOM." This matters beyond plain accessibility hygiene: Profiles carousel v2's card opens its settings disclosure on focus as well as hover, and without this fix, selecting a country left that focus in limbo and the disclosure stuck open indefinitely. Opens instantly with no animation flourish (no Framer Motion on the popover itself), per spec. Rendered directly above the primary CTA — inside `Hybrid.tsx`'s centered action area, and inside `HybridSplit.tsx`'s left rail — gated on `plan === "plus" && phase === "unprotected"` so it disappears the moment the CTA's own lifecycle moves past `unprotected`, and never renders (or reserves space) at all for Free. The selector and CTA share one translucent, rounded action-area container; that **entire connection card** (container + selector + button) animates in together at `HYBRID_TIMING.ctaAppear` — the last step in Hybrid's Act 1 entrance sequence, after the activity cards settle — rather than only the button animating independently.

**Cycling activity card (`showCountrySelect` only).** When the country selector is showing, the usual 3-stacked-card activity list is swapped for a single card (`versions/hybrid/CyclingActivityCard.tsx`) whose icon + text roll through the same `HYBRID_CARDS` pool every 3s in a vertical slot-machine-style reel (`AnimatePresence`, `y` travel + fade, snappy `easeOut`-family curve) — the eye/label indicator on the right is fixed to the card's own redact/seal state (not per-entry) and doesn't roll. One card persists through connecting AND protected too (rather than reverting to showing 3, or hiding cards); its eye/label transitions Visible → Hiding… → Hidden exactly like the 3-card variant's per-card indicators do. The reel itself only pauses for the brief "connecting" transition (`paused` prop, tied to `phase === "connecting"`) — once protected, it keeps spinning through entries indefinitely with the label staying on "Hidden," rather than freezing. Both `Hybrid.tsx` and `HybridSplit.tsx` branch on `showCountrySelect` at render time: `true` renders `CyclingActivityCard`, `false` renders the original `HYBRID_CARDS.slice(0, revealedCount).map(...)` stack, byte-for-byte unchanged. Both branches reuse the same `useHybridReveal` timing (`revealedCount`/`redactCount`/`sealed`) so the cycling card appears/redacts/seals at the identical beats the 3-card stack always has — only the rendering differs, not the choreography. The cards region's `min-h-[164px]` reservation (which keeps the location chip above from drifting as cards reveal) is skipped when cycling, since a single fixed-height card never changes height regardless of which entry or act is active.

**Selection state lives in `OnboardingV2`** (`selectedCountry: string | null`, `null` = "Fastest country") — single source of truth, threaded down to `Hybrid`/`HybridSplit` as `selectedCountry`/`onSelectCountry`, same pattern as `hybridPinOffsetY`. Selecting a country updates ONLY `CountrySelect`'s own trigger label — the hard requirement that the unprotected chip/map/pin/cards/copy keep showing the user's REAL exposure until connecting is structurally guaranteed, not just accidentally correct: `LocationChip`'s pre-connect branch (`phase !== "protected"`) renders exclusively from its `country`/`countryCode`/`ip` props (always `geo.country`/`geo.countryCode`/`geo.ip` — real IP-detected values), and the shared map's `mapLat`/`mapLng` only reads the resolved destination when `isProtectedSide` is true — `selectedCountry` is simply never consulted by either while unprotected.

**`resolveVpnDestination`** (`lib/server.ts`) resolves a `VpnDestination` (`{ country, countryCode, lat, lng, vpnIp }`) from `selectedCountry`: `null` (or a name absent from the data, which shouldn't happen) falls back to the existing `VPN_SERVER` constant (Netherlands, "Fastest country"'s resolution, unchanged); an explicit selection looks up real coordinates (`countryMarkers`) and a real ISO/flag (`getIsoCode`) for that name. **VPN IP honesty:** there is only one VPN IP anywhere in this app's data (`VPN_SERVER.vpnIp`) — no per-country IP list exists — so every resolved destination reuses that same demo value (confirmed at checkpoint: an honest shared placeholder already used everywhere else in this prototype for "a resolved VPN connection," not a fabricated new IP per country).

**On connect**, `handleProtect` (`OnboardingV2.tsx`) is unchanged in signature — it reads `selectedCountry` via closure rather than needing a parameter threaded through every version's `onProtect: () => void` contract, so v1/v2/v4/v4-split are untouched. Once `onSucceed` fires, the protected chip (`vpnCountry`/`vpnCountryCode`/`vpnIp` props on `LocationChip`, replacing its former direct `VPN_SERVER` import) and the shared map's flyTo destination (`mapLat`/`mapLng`, now sourced from `protectedDestination` instead of `VPN_SERVER` directly) both resolve to the SAME `resolveVpnDestination(selectedCountry)` value — so a Plus user who picked Japan sees Japan's flag/name in the chip and the map flying to Japan's real coordinates, never the literal string "Fastest country" and never a guessed destination. Free-plan and non-Hybrid runs are unaffected: `selectedCountry` is always `null` for them (no UI ever sets it), so `resolveVpnDestination(null)` always equals the prior hardcoded `VPN_SERVER` value exactly.

**Interaction with the connection-failure path:** the Tier 1 "different country" auto-remedy narration (`CONNECTION_RETRY_NARRATION.remedy1`, "Trying a different location…") never actually changes the simulated destination either way — it's cosmetic headline text — but would misleadingly imply a country swap while an explicit Plus selection is active. `useConnectionAttempt` gained an optional `hasExplicitCountry` flag (`OnboardingV2` passes `selectedCountry !== null`); when true, the `remedy1` narration slot substitutes `remedy2`'s copy ("Trying a different way to connect…") instead, so an explicit choice is never silently narrated as overridden — defensive insurance, since this cause pairing (`network-blocks-vpn`/`generic`, the only causes with a 3-slot remedy sequence) is currently unreachable via the simplified 4-preset `FAILURE_SIM_PRESETS` dropdown anyway.

**Analytics:** `ConnectionFailureAnalyticsPayload` gained `selectedCountry` (fired on `connection_attempt_start` — what the user chose, `null` for "Fastest country") and `resolvedCountry` (fired on `connection_resolved` — what actually connected, always a real country name).

**Known limitation (accepted, not a bug):** the shared map's flyTo destination (`mapLat`/`mapLng`) is version-agnostic (there is only one persistent map instance), so it does read `protectedDestination` regardless of which connection-stage version is active. v1/v2's own `InfoCard`/`ControlPanelOverlay` rows, however, were intentionally left reading `VPN_SERVER` directly (out of scope per the "Hybrid/Hybrid Split only" decision) — if a Plus user picked a country on Hybrid and then switched versions via the prototype HUD before connecting, the map would fly to the picked country while v1's own text row would still say "Netherlands." This is only reachable by prototype-HUD tinkering mid-flow, not by any real user journey (a real Plus user stays on one version through connecting), so it was accepted rather than expanding scope.

## Tone of voice (content axis — Stages 1 & 2)

A third prototype-controls dropdown, **"Tone of voice"**, rewrites copy **content only** — every layout, concept, animation and timing is untouched. It is orthogonal to the Version/Concept selectors, so any of the five connection layouts (Location map spotlight Centered `v1` / Split `v2`; Browsing experience Centered `v4` / Split `v4-split`; Hybrid Centered) — or, for stage 2, any of the 4 tuning concepts — can be rendered in any tone. The axis is `ToneOfVoice` (`"straightforward" | "reassuring" | "empowering" | "educational"`, `lib/toneOfVoice.tsx`), backed by a single **global** `tone` state in `App.tsx`, threaded down through the `tone` prop on `OnboardingV2` to whichever stage/variant is active. The dropdown is shown only for stages listed in `STAGE_SUPPORTS_TONE` — originally connection-only; **stage 2 ("tuning") now opts in too**, exactly per the pattern's own design intent ("the structure is deliberately generic so other stages can opt in later: add their copy shape here and add the stage to `STAGE_SUPPORTS_TONE`"). This confirms the selector was always meant to be one global control with per-stage opt-in visibility, not a separate mechanism per stage.

### Stage 1 (connection)

All connection copy lives in `CONNECTION_COPY[tone]`, split into `mapSpotlight` (headline/subtext/CTA/split-view card headings for `v1`/`v2`, with phase-colored accent spans and ISP interpolation), `browsing` (the `BrowsingCopy` object for `v4`/`v4-split`: headlines, sub, CTA, connecting/protected headlines, seal card, continue, `visibleLabel`, and the per-entry lock labels `redactingLabel`/`sealedLabel`), and `hybrid` (the `HybridCopy` object for Hybrid: `exposedHeadline`/`exposedSub`/`connectingHeadline`/`protectedHeadline`/`protectedSub`/`ctaProtect` — Hybrid's cards reuse `browsing`'s `visibleLabel`/`redactingLabel`/`sealedLabel` rather than duplicating them). `mapSpotlight`/`hybrid` `exposedSub`/`protectedSub` each supply **known** (named ISP + "others along the way/in between") and **unknown** (broad phrasing, no name) variants via `ispCopy()` + `resolveIspKnown(geo)` — honest broadening beyond ISP-only blame (provider, networks, sites visited). `OnboardingV2` reads `mapSpotlight` inline for `v1`/`v2`, passes `browsing` down as the `copy` prop to the diary components, and passes `tone` straight through to `Hybrid` (which reads `hybrid` + `browsing` itself); `ActivityFeed`/`ActivityEntry` take `redactingLabel`/`sealedLabel` as props (previously hardcoded "Protecting…"/"Protected"; the straightforward tone's values are now "Hiding…"/"Hidden", to match the crossed-out-eye icon rather than the earlier padlock-style wording). Hybrid card main-line text lives in `versions/hybrid/data/hybridActivityEntries.ts`; v4's tone-invariant diary entries in `activityEntries.ts` are unchanged.

The four tones:
- **Straightforward** (default — the original shipped copy): factual, calm, professional. e.g. "Your online identity is currently unprotected" / diary card mark "Hiding…" → "Hidden".
- **Reassuring**: warm, empathetic, peace-of-mind. e.g. "Right now, this connection isn't private" / CTA "Make my connection private" / lock "Securing…" → "Private".
- **Empowering**: agency and control. e.g. "You decide who sees you online" / CTA "Take control" / "You're back in control" / lock "Claiming…" → "Yours".
- **Educational**: expert clarity, explains the mechanism. e.g. "Here's what your network can see" / CTA "Encrypt my connection" / "Your traffic is now encrypted" / lock "Encrypting…" → "Encrypted".

### Stage 2 (tuning)

Every copy surface across the picker + tuned-result step is tone-aware: `JtbdGridPanel`'s title/subtitle; the tuned-result header's intro subtext, the "{verb} for {jtbd}…"/"{verb} for {jtbd}" title pair, and the completion summary; and every JTBD's 2 enabled + 2 paid feature **outcome** sentences and its **tip**, across all 4 layouts and all 6 JTBDs.

**Structural copy** — `TuningCopy` (`lib/toneOfVoice.tsx`), a `Record<ToneOfVoice, TuningCopy>` named `TUNING_COPY` (unrelated to, and a full replacement for, the *different*, now-deleted `TUNING_COPY` that used to live in `versions/lib/tuning.ts` before the tuning-stage consolidation — pure naming coincidence, no shared history):
```ts
interface TuningCopy {
  pickerTitle: string;
  pickerSubtitle: string;
  introSubtext: string;
  titleDuring: (jtbdWord: string) => string;
  titleComplete: (jtbdWord: string) => string;
  summarySubtext: (applied: number, locked: number) => string;
}
```
`JtbdGridPanel` reads `pickerTitle`/`pickerSubtitle` directly from `TUNING_COPY[tone]`. `tuned-result/copy.ts`'s `introSubtext`/`titleDuring`/`titleComplete`/`summarySubtext` functions were changed to take a `tone` parameter and delegate into `TUNING_COPY[tone] ?? TUNING_COPY.straightforward` (the fallback-to-straightforward on a missing tone every tone-aware function in this stage implements). `counterSubtext` ("Applying X of N settings") took no `tone` parameter change — it's one of the strings kept constant (see below).

**Per-JTBD copy** (outcomes + tips) — a *separate* file, `lib/jtbdTuningToneCopy.ts`, a sibling of the base `lib/jtbdTuningResult.ts` it re-voices: `JTBD_TONE_OUTCOMES: Record<ToneOfVoice, Record<JtbdId, JtbdToneOutcomes>>` where `JtbdToneOutcomes = { enabled: [string,string]; paid: [string,string]; tip: string | null }`, mirroring the base data's tuple shape/order exactly (`enabled` is Protocol then Kill Switch). Deliberately NOT folded into `toneOfVoice.tsx` — cramming 6 JTBDs' worth of outcome sentences into that file would break the "one file per content concern" convention every other data file here follows (`jtbdData.ts`, `jtbdUpsell.ts`, etc.); `straightforward`'s entries are *built directly from* `JTBD_TUNING_RESULT`'s existing `outcome`/`tip` fields (not hand-copied) so the two can never drift. The three non-straightforward tones re-voice the same plain-language facts in each tone's register (no VPN jargon in benefit lines). Two lookup helpers, `toneOutcome(tone, jtbdId, "enabled"|"paid", index)` and `toneTip(tone, jtbdId)`, both fall back to `straightforward` on a missing tone. The base data (`settingsName`/`value`/`featureName`/`asset`/`tooltip`) is **never** re-voiced or touched — only the plain-language `outcome`/`tip` text changes.

**Wiring into the layouts:** all 4 (`StackedLayout`/`CompactListLayout`/`SplitByStatusLayout`/`CardGridLayout`) gained a `tone` prop. `StackedLayout` (whose resolved row JSX is bespoke, not `EnabledFeatureRow`/`PaidFeatureRow`) calls `toneOutcome(...)` directly in place of `feature.outcome` and renders an (i) Radix tooltip beside each settings/feature label (reuses `versions/upsell/lib/InfoTooltip.tsx`). The other three reuse `EnabledFeatureRow`/`PaidFeatureRow` — each layout builds a `{ ...feature, outcome: toneOutcome(...) }` shallow copy before rendering, so only the outcome text is swapped and every other field (settings name, value, feature name, asset, tooltip) passes through untouched. The tip lookup (`toneTip`) exists as data for completeness but isn't rendered by any current layout.

**Confirmed CONSTANT across all 4 tones** (checkpoint): the 6 JTBD option labels (`JTBD_OPTIONS`), technical settings names/values/feature names/decorative assets (all of `JTBD_TUNING_RESULT` except `outcome`/`tip`), the "Available with VPN Plus" badge + Split by Status column headers (`TUNED_RESULT_COPY`), the counter format ("Applying X of N settings"), the picker's witty "wink" line (`JTBD_WINK_COPY`), the per-row narration verbs ("Enabling…"/"Checking…", `narrateEnabling`/`narrateChecking`), and the neutral navigation labels ("Go to app directly", Back, the pre-selection "Continue", and the dynamic "Tune for {jtbd}" CTA, `JTBD_CONTINUE_LABEL` / `JTBD_GO_TO_APP_LABEL`) — this last group mirrors stage 1's own precedent, where `browsing.continue` is likewise the literal string `"Continue"` in all 4 tones; only the more expressive/emotive strings vary by tone in either stage.

**Analytics:** no analytics infrastructure exists anywhere in this repo (confirmed again during this change) — consistent with every other tone-aware surface, no events are fired for tone changes.

## Tuning-stage: single consolidated flow + result layouts

The "Personalized JTBD tuning" stage was **consolidated from 5 separate versions into ONE flow**, formerly the "Visual Tuning" version's mechanics — picker → no separate loader → a result step that opens with its own centered intro and materializes its 4 settings one at a time. The 5 selectable JTBD-tuning versions that used to exist (Default, Loadouts, Split by Status, Card Grid, Visual Tuning) are gone as *versions*; three of their result designs survive as **result LAYOUTS** of the one consolidated flow — Loadouts did not survive in any form (it was a fully self-contained morphing-card scene with no reusable result "arrangement" concept, and nothing else in the codebase depended on it or its `TuningStageVersionProps` contract, confirmed before removal). The bottom prototype selector that used to pick a "Version" for this stage now picks this **Layout** instead.

**Files removed in the consolidation:** `JtbdPanel.tsx` (the old two-column radio-list picker — `JtbdGridPanel` is now the stage's only picker), `components/TuningLoaderState.tsx` (the separate "Tuning the app for you…" loader — no longer used by anything), `components/TunedResultState.tsx` (the old "Default" result screen), `versions/tuning-loadouts/` (entire folder), `versions/tuning-split-by-status/`, `versions/tuning-card-grid/`, `versions/tuning-visual-tuning/` (the latter three's designs live on as `tuned-result/layouts/*` instead — see below), and `versions/lib/tuning.ts` (`TuningStageVersionProps`/`JTBD_ORDER`/`TUNING_COPY`, used only by Loadouts). `EnabledFeatureRow`/`PaidFeatureRow` were **kept unchanged** — they're still reused both by the new layouts and by the untouched, downstream `PlusWelcomeState`.

**The tip footnote was removed from every result-style screen** (`TunedResult` — all 4 layouts — and `PlusWelcomeState`, since it re-shows the same content). `components/TuningTip.tsx` was deleted (it had no other callers left); `JTBD_TUNING_RESULT`'s `tip` field is left in the data unchanged (still populated per-JTBD) but is simply never read by any component now. `useTunedMaterialization`'s `continueDelayMs` no longer waits on a tip gap — Continue fades in directly after the last item resolves.

### The single flow

1. **Picker** (`JtbdGridPanel`, phase `jtbd`) — unchanged from before this consolidation (3×2 grid, wink message, dynamic Continue label, toggle-to-deselect). `onContinue` now unconditionally advances straight to phase `tuned` — there is no `tuning` (loader) phase left in the `Phase` type at all.
2. **Result step** (`TunedResult`, phase `tuned`, `src/app/onboarding-v2/tuned-result/TunedResult.tsx`) — the sole result component, parameterized by a `layout: ResultLayout` prop (`"stacked" | "split-by-status" | "card-grid" | "compact-list"`, default `"stacked"`). Runs, identically for every layout:
   - **Centered intro** — the header block (loader `Spinner` + "Tuning for {jtbd}…" + a static "Applying the settings to optimize the experience for you." subtext) fades in centered on screen and holds there for `centerHold` (2000ms).
   - **Move to top** — the SAME block (one persistent `motion.div`, Framer's `layout` prop drives the FLIP from a `justify-center`→`justify-start` wrapper toggle, never unmounted) travels to its top position over `moveToTop` (600ms); the spinner crossfades (true overlap, not sequential) into the JTBD's category icon (`JTBD_ICONS`, same fixed 48×48 slot, no size jump) and the subtext crossfades to the live "Applying {X} of {N} settings" counter. Reduced motion skips the travel animation entirely (renders top-anchored from the start; `layout` disabled) and only holds briefly (`reducedIntroHold`, 500ms) before the same crossfades fire.
   - **Materialization** — only once the block has landed do the 4 settings items begin their two-phase reveal, one at a time (Phase 1: narrated spinner "Enabling {setting}…"/"Checking {feature}…"; Phase 2, ~300ms: resolves into the finished visual). The counter's X is `rowMounted.filter(Boolean).length` — derived directly from the same row-progression state the items render from (no separate counter variable), incrementing the instant each item's Phase-1 spinner is scheduled (both free and locked items count, 1..4). A free/paid **boundary beat** (an extra pause, `boundaryIn + rowGap`) is reserved before the first locked item begins in every layout's timing, even layouts (Card Grid) that don't render a visible widget there — this keeps total pacing identical across all 4 layouts, per the "centralize timing in one shared config" requirement.
   - **Completion** — once the last item resolves, the title crossfades to "Tuned for {jtbd}" (same sentence structure as the "during" form, just the verb/ellipsis change, so it reads as a simple word swap) and the subtext to the derived "{applied} settings applied · {locked} available with VPN Plus" summary (the "· {locked}…" clause is dropped entirely, not shown as "0 available", for Plus users); Continue fades in and becomes interactive. No tip footnote anywhere in this step (removed across all 4 layouts — see below). `{jtbd}` is `result.jtbdLabel.toLowerCase()` throughout — already the project's agreed gerund short form for bypass ("Bypassing restrictions"), so no separate lookup table is needed.
3. `OnboardingV2` keys `<TunedResult key={resultLayout} .../>` by the selected layout, so **switching the Layout selector remounts the whole component and replays the sequence from the centered intro** in the newly chosen arrangement — confirmed as the desired prototype behavior (so reviewers can see the full intro + materialization in any layout, not just its static end state), rather than jumping straight to a completed state.

Only the RESOLVED ARRANGEMENT of the 4 items — and which "shape" their Phase-1 placeholder takes — differs per layout; the intro, header move, counter, completion strings, and Continue are 100% shared, driven by one hook (`useTunedMaterialization`) and one timing config (`TUNED_RESULT_TIMING`, in `tuned-result/timing.ts`) with no per-layout timing overrides.

### Free minimal list content (Stacked + Free only)

One arrangement/plan combination has its own body rather than its own layout component: **Stacked + Free**, which is the only way stage 2 ever renders the default concept today (`layout="stacked"` is hardcoded, and Plus users are the other branch). `TunedResult` builds `freeMinimal` (`tuned-result/freeMinimalContent.ts`) whenever `layout === "stacked" && userPlan === "free"` and renders `tuned-result/FreeMinimalList.tsx` in place of `StackedLayout`. Everything else — the Plus path, and the other three arrangements stage 3's Plus Welcome reuses — goes through `StackedLayout` unchanged.

Three things differ from what `StackedLayout` renders on the same data:

- **No "Available with VPN Plus" section at all** — no `BoundaryDivider`, no `ProfilesSummaryRow`, no locked feature rows. `boundaryIndex` is pushed out of range exactly the way the Plus plan already pushes it, so the shared schedule skips both the divider and its pacing pause. The rationale is that the whole screen is now about what the user already has, and the upsell this section used to preview inline is the immediately following stage anyway.
- **The two settings are Protocol and Auto Connect**, not Protocol and Kill Switch. Protocol still comes from the shared data via `mergeFreeSettings` — same per-intent value, same "strictest wins" conflict resolution, same tone-voiced sentence through `toneOutcome`. **Auto Connect is modelled only here**, in `AUTO_CONNECT` (`freeMinimalContent.ts`), keyed by `JtbdId` for its per-intent sentence; the chip always reads `"On"`, meaning Proton VPN starts when the computer launches and connects automatically. The shared `AUTO_CONNECT_TOOLTIP` explains that behaviour, per the `PROTOCOL_TOOLTIP`/`KILL_SWITCH_TOOLTIP` precedent.
- **2–3 value claims sit below the settings, with no chip.** They're statements that are already true of Proton VPN Free for that intent (no-logs and independently audited, Swiss jurisdiction, open-source apps, unlimited data, no ads) rather than settings anything just changed — so there is no setting name to put in a chip, and the missing chip is the entire signal that distinguishes them. `VALUE_CLAIMS` holds three per intent, most-relevant first; `FREE_MINIMAL_CLAIM_CAP` (3) is the display ceiling.

**Merge rules across a multi-intent selection.** Protocol reuses `mergeFreeSettings` verbatim. **Auto Connect resolves as "first-selected intent wins, outright"** for its sentence — the chip is always `"On"`, so there's no value/sentence pair to keep in sync, but the outcome still needs to match the user's primary intent. (This sidesteps the "merged row copy vs. resolved value" open item recorded further down for the shared merge.) **Claims are gathered round-robin** — first claim of each selected intent, then second, and so on — deduplicated by text and capped at 3, so with 3 intents selected the user sees one claim per intent rather than all three from whichever they picked first.

**Header copy.** The counter can only speak for the settings rows, so it counts to `settings.length` (2) and then hands over to `FREE_MINIMAL_CLAIMS_COUNTER` ("Confirming what's already included…", `tuned-result/copy.ts`) while the claim rows arrive; `claimsPhase` also drives the crossfade key, without which the handover would be an instant mid-sentence text swap. The completion subtext is `summarySubtext(tone, 2, 0)` — the settings it actually applied, and no locked clause, since the claims were never counted as settings.

**Tone.** Protocol's sentence is tone-voiced. Auto Connect's and the claims' are not — they exist only on this path and have no entries in `JTBD_TONE_OUTCOMES`, so they read identically in all four tones. Same fallback-to-`straightforward` precedent the Multiple-mode strings in `lib/toneOfVoice.tsx` already set.

**Row budget.** 5 rows (2 settings + 3 claims) at every selection size from 1 to 6 intents, against ~440px of list space in the 768px-tall window — comfortable even if every row wraps to two lines. Total materialization runs ~10s (5 rows × 1500ms + the 2.6s intro), just under the 6-row `pacingGuardRowThreshold` at which `spinnerHold` would compress.

**Shared row primitives.** `SettingLabelPill`, the row's outer class and the check-pop variants moved out of `StackedLayout.tsx` into `tuned-result/stackedRow.tsx` so `FreeMinimalList`'s rows are literally the same object rather than a lookalike that can drift. `StackedLayout` keeps what only it uses (the locked-row settle variants, `FeatureLabel`/`FeatureNamePill`).

### Profiles-first tuning concepts (`tuned-result/profiles/` + `concepts/profiles-*/`)

A second exploration on the same `TuningConcept` axis, bringing it to 9 members at the time (12 now). Where the 3 concepts above treat the applied SETTINGS as the outcome, these 5 treat **profiles as the primary outcome** and demote or reframe the settings. Built from the specs in `docs/specs/profiles-tuning/`, which remain the design rationale of record; this section documents what shipped.

Labelled `"Profiles — …"` in the Concept dropdown, because a list this long needs the explorations visually separable. `App.tsx` needed no change — the HUD maps over the exported concept list.

**Three things these need that didn't exist:**

1. **`lib/jtbdProfiles.ts`** — `TunedProfile`, the first profile object in the codebase that is more than a label. Adds a destination (`country`/`countryLabel`), whether Free can reach it (`freeRunnable`), and two plain-language sentences: `effectSentence` ("Use this and Proton VPN connects you…") for concepts presenting profiles standalone, and `deltaSentence` ("Everything above, plus…") for concepts framing them as additions to the baseline. Both tone-CONSTANT, no jargon, no third-party service names. `ProfilePreview`/`buildProfilePreviews` in `lib/jtbdMerge.ts` are untouched — the default concept and the 3 above still use them.
   - **Settings are derived, never authored:** `profileSettings(jtbd)` reads `JTBD_TUNING_RESULT[jtbd].enabled`, so a profile can't claim a value the screen doesn't apply.
   - **`effectiveProfileSettings(jtbd, baselineSettings)` is the correctness rule that matters most.** In Multiple mode the baseline is the *merged* union, so one intent's own value can be WEAKER than what's already applied — Gaming + Privacy merges Kill Switch to "Advanced" while Gaming's own value is "Standard". Rendering the raw value would tell the user that using the Gaming shortcut lowers their protection, which is untrue. Every concept displays effective settings; `ProfileCard` takes them as a required prop rather than deriving them, putting the rule at the component boundary instead of trusting each call site. `strictestOf(primary, other)` is the shared primitive (also used for combined drafts, which merge several intents).
   - **`FREE_TIER_COUNTRIES` / `isFreeRunnable`.** **[UNVERIFIED]** — this describes the *prototype's* behaviour (Free resolves every connection to the single `VPN_SERVER`, Netherlands), not the real product's free country list. Nothing states a count of free countries. `bypass` is deliberately not free-runnable despite a null country: its rule targets the fastest server *outside* your own, which is the Plus "Fastest outside-country" feature.
   - **Accent colours** are all seeded to the primary purple. **[UNVERIFIED]** — a six-colour categorical palette needs design sign-off, and no concept depends on colour to carry meaning (identity comes from the glyph and the name).
2. **Plan awareness.** `TuningConceptProps.userPlan?: SessionPlan` defaults to `"free"`, so the 3 existing concepts need no edit and behave identically — they never pass it. The 5 profiles concepts branch on it and render a real Plus state, which is why their Continue uses the same plan-aware routing `TunedResult` does (`plan === "plus" ? handleExit(…) : setPhase("upsell")`) rather than the 3 concepts' unconditional `setPhase("upsell")` — sending a Plus user to the upsell right after showing them their live profiles would contradict what they just saw.
3. **`profiles/useProfilesConceptData.ts`** — a sibling of `useTuningConceptData`, not a parameterization of it. `useTuningConceptData` is **deliberately unmodified**: it's load-bearing for the 3 existing concepts, and it only emits a profiles row when Multiple mode is active, so a single-intent run produces no profile at all — structurally unusable for concepts whose whole subject is profiles. The new hook's schedule is one row per profile, **always**: `settingRows` (indices `0..s-1`) → `profileRows` (`s..s+p-1`) → `plusFeatureRows`. Everything governing FEEL is still shared, not rebuilt: the same merge → rank → cap engine, the same `useTunedMaterialization` (called once), the same tone helpers. The free/Plus boundary sits at `settingRows.length` (profiles are the first Plus-only thing revealed), or past the end on Plus so the boundary pause is skipped. Plus features are capped at `paidFeatureCap` in BOTH modes, unlike the older hook, because a single-mode screen with one profile and two competing feature rows would bury the subject.

`ConceptFrame` was widened to accept either hook without a union or a cast: the 12 fields it reads are extracted as `ConceptFrameData` in `concepts/types.ts`, `TuningConceptData extends` it, and the `data` prop is narrowed to it. Structurally equivalent for existing callers. **The 5 concepts:**

1. **`profiles-baseline` — Baseline + shortcuts.** Two visually distinct registers: a compact, bright, already-on `ProtectionAnchor`, and beneath it a majority-of-the-screen tier of optional shortcut tiles. The layout itself says "you're covered either way". The free answer is architectural — the free outcome owns the hierarchy while the Plus outcome owns the square footage — so it needs no new entitlement. The smallest departure from what exists, and the recommended starting point.
2. **`profiles-rehearsal` — Rehearsal stage.** One persistent stage plus tiles the user can rehearse. Pressing one plays what it would do, then the stage **returns** to the protected baseline, every time. The return is the concept: it turns "will I break something?" from a claim into a behaviour the user watches repeatedly. `useRehearsal` owns the state machine (interruption cancels cleanly; all timers cleared on unmount) and builds narration from the profile's own data rather than six authored scripts. Nothing says "connected" — a rehearsal is a demonstration. Rehearsing is free; *keeping* is where the Plus badge sits. Its "Rehearse everything" action is the only place a user can act on the combination instinct directly, ending on the baseline to show the combined setup already exists.
3. **`profiles-shelf` — Shelf gallery.** Breadth-first: a grid where the first cell is the user's own protection (`BaselineCard`) and the rest are their profiles as peers. Adaptive density keeps the height stable (2–4 cells at `card`/2 cols, 5–7 at `tile`/3 cols), at the cost of the per-card settings chips at exactly the selection counts where users picked the most. `BaselineCard` is deliberately separate from `ProfileCard` — it represents an always-on state, not a shortcut — which means their geometry must be kept identical by hand. Uses `effectSentence`, not `deltaSentence`, since cards here stand alone. **Known weakness:** the baseline card must win a hierarchy contest against up to six same-sized neighbours, and one active card among six locked ones can read as a value ratio however well it's placed.
4. **`profiles-deck` — Focused deck.** Depth-first: one card at a time with a before-and-after (`ComparisonStrip`) of exactly what it changes, over three fixed plain-language questions, plus a trailing "Everything at once" card for the baseline. Settings stop being an outcome and become the "Now" column — a job rather than a slot. **The "No change" rows are the feature, not a bug:** since `effectiveProfileSettings` guarantees a profile is never weaker than the baseline, rows 2 and 3 usually read unchanged, which is precisely the reassuring truth that using a shortcut changes *where* you connect, not *how protected* you are. Hiding them for looking repetitive would discard the concept's strongest evidence. **Two unsettled external dependencies, so "Try it now" is a prototype demonstration that marks the card tried rather than actually applying and reverting anything:** (a) whether one-time free application is offered at all, and (b) whether settings can be applied and cleanly reverted in-session — `useConnectionAttempt` has no notion of a temporary settings change.
5. **`profiles-draft` — Editable drafts.** The screen produces a proposal, not a verdict: the user renames drafts, drops them, combines them, and watches a live sidebar preview assemble. The only concept that hands over authorship, and the strongest answer to "why not one profile with all of them?" — the user simply does it. `useDrafts` owns the model, seeded once via a `useState` initialiser (an effect-based seed would wipe edits every time the materialization timer fired). Combination rules: settings are the strictest-wins union via the existing `mergeFreeSettings`, then re-checked against the baseline, so a combination is never weaker than any of its parts; destination keeps a shared label or honestly falls back to fastest-country with the row saying so, since one connection can't be in two countries; splitting restores the sources' original names, which is what makes combining safe to try. `DraftNameInput` is the one genuinely new interaction on this screen — click-to-edit so the default state reads as a list rather than a form, Enter/blur commit, Escape reverts, empty reverts silently, duplicates allowed (the real app permits them). **Its free quota of 1 is an unsettled product decision**, flagged in the code, and it deliberately contradicts today's disabled-on-Free sidebar behaviour. Its cost is engagement: understanding comes from editing, so a user who wants to click Continue and leave learns less here than on any of the other four.

**Copy & timing:** the 5 new `TUNING_CONCEPTS_COPY` keys hold each concept's own structural labels; shared strings live in `profilesCopy.ts`. `TUNING_CONCEPT_TIMING` gained `rehearseTravelMs`/`rehearseStepMs`/`rehearseHoldMs`/`rehearseReturnMs` and `deckSlideMs` — all timing USER-TRIGGERED interactions that happen after the shared materialization finishes, so none can affect pacing on any other concept. `TUNED_RESULT_TIMING` is untouched. With six intents selected the schedule reaches 9 rows, past `pacingGuardRowThreshold`, so the existing `spinnerHoldCompressed` compression engages automatically — no new pacing logic anywhere.

**Analytics:** each concept exports its id constant and passes it to `ConceptFrame`'s `concept` prop, so `useTrackTuningView`/`trackTuningEvent` pick it up with no extra wiring — same as `CHECKLIST_CONCEPT`.

### Profile-first (Plus-only) — `concepts/profile-first/`

The tenth concept, and the first **plan-gated** one (the two carousels below are the second and third). Where the 5 above each need an answer to "what does a Free user get out of this screen", `profile-first` declines the question: it is offered only on a Plus run, so nothing on it is locked, hedged, or aspirational. That single constraint is what buys the layout its confidence — one profile at full size with a photograph and a real configuration, instead of a grid of tiles hedging about what a shortcut might do once you pay.

**The gate**, shared with both carousels. `PLUS_ONLY_TUNING_CONCEPTS` (in `OnboardingV2.tsx`) lists the Plus-only ids, and `FREE_ONLY_TUNING_CONCEPTS` its mirror image (one entry, `profiles-carousel-v2-free`). Two exported helpers act on both lists, each excluding whichever set was designed for the other plan:

- `tuningConceptsForPlan(plan)` — what the HUD's Concept dropdown lists. A Free run doesn't see the Plus-only options, and a Plus run doesn't see the Free-only one.
- `effectiveTuningConcept(concept, plan)` — coerces a stale selection back to `defaultTuningConceptForPlan(plan)`. Needed because the Concept dropdown and the **Plan** control live on different screens (`PrototypeControls` vs. `SignInPlanControl`), so a reviewer can pick `profile-first` on a Plus run and then start a Free one with that selection still in `App.tsx` state — and, since the Free-only concept landed, the reverse as well. `App.tsx` applies it both to the `<select>`'s value and to `OnboardingV2`'s `tuningConcept` prop.

`PrototypeControls` gained a read-only `plan` prop for this; the control that *sets* the plan is unchanged and still lives on Sign In. Because the gate holds, the component itself carries **no plan branching at all** — it doesn't accept `userPlan`, and its Continue has one destination (`handleExit(…, "plus")`) rather than the 5 profiles concepts' plan-aware ternary.

**Three claims, three materializing rows.** The screen asserts the profiles (row 0, the tabs and card as ONE row — revealing a control before the thing it controls would show tabs with nothing to switch), then two standalone Plus features (rows 1–2).

**`useProfileFirstData`** is a third sibling of `useTuningConceptData`/`useProfilesConceptData` rather than a mode on either, for one structural reason: this concept has **no baseline settings rows**. The profiles absorb the settings entirely — a profile carries Protocol itself — and both existing hooks emit per-setting rows this layout has nowhere to put. Everything governing FEEL is still shared: the same `useTunedMaterialization` (called once) and the same merge/rank engine. There is no free/Plus boundary, so `boundaryIndex` is pushed past the end and the boundary pause is skipped rather than inserting a beat with no visible cause.

**`lib/jtbdProfileConfig.ts` — the one place this concept adds authored data.** The design calls for four configuration rows per profile: NetShield, Port forwarding, Protocol, NAT type. Only Protocol existed. The tuning data models NetShield, Port Forwarding and Moderate NAT as *unvalued Plus features* (a name and a benefit sentence, no On/Off), and has no NAT-type vocabulary at all.

- **Protocol is derived** from `JTBD_TUNING_RESULT[jtbd].enabled[0]`, so the card can't claim a protocol the tuning step doesn't apply. Name and destination come from `JTBD_PROFILES`.
- **The other three are authored** in a single `CONFIG_VALUES` table, with a stated per-intent rationale so each value is arguable rather than arbitrary: NetShield is off wherever DNS filtering plausibly gets in the way (streaming, gaming, bypass) and on for the other three; Port forwarding is on only where something needs to reach you (downloading, gaming); NAT type is Moderate only for gaming, matching the real "Moderate NAT" Plus feature that intent already carries, and Strict elsewhere. **[UNVERIFIED]** — prototype values pending product sign-off; change them in that one table.
- **Tooltips are per-VALUE, not per-label** — "NetShield: Off" and "NetShield: On" need genuinely different explanations. The On-state strings are looked up from the tuning data by feature name rather than re-typed, so they can't drift; only the two off-states and the strict-NAT state are newly written.
- **The four labels are fixed for every profile**, so switching tabs changes values in place instead of reflowing the list. That is what makes the tabs read as a comparison.

**The two Plus features below the card are derived, and can never duplicate the card.** `CONFIGURED_FEATURE_NAMES` lists the three feature names the card accounts for, and `plusFeaturesFor` excludes them — a card reading "NetShield: Off" directly above a row reading "NetShield — On" reads as a bug, not as a profile override. It then prefers the user's own selection, ranked by the existing `FEATURES_RANK`, and only tops up from the full 12-feature union when the selection leaves fewer than two. The top-up covers real cases, not hypothetical ones: a single-intent run on streaming, gaming or downloading contributes only 2 features, one of which the card already covers. It misdescribes nothing, since these rows are explicitly the Plus features that are *not* part of a profile's configuration. The count is a local `PLUS_FEATURE_COUNT = 2`, deliberately **not** `TUNED_RESULT_TIMING.paidFeatureCap` (1) — that cap exists so a lone feature row can't bury the other concepts' profiles *summary* row, whereas here the profiles are a full-width card nothing can bury. Local, so it can't alter any other concept's pacing.

**Assets — the one place the "no new artwork" rule is relaxed**, at the user's explicit request. Six per-intent photographs (`assets/profile-photo-{intent}.jpg`, ~400 KB total) were generated for this concept and are now shared with `profiles-carousel`, since the repo had no per-intent imagery. They are deliberately uniform — night-time, desaturated, cool shadows with a violet cast, no faces, no legible screens — because that uniformity is what lets six tabs read as one family of profiles rather than six unrelated stock photos. Everything else reuses existing assets.

### Profiles carousel v1 (Plus-only) — `concepts/profiles-carousel/`

The eleventh concept, and the second plan-gated one. Labelled "v1" in the Concept dropdown since v2 landed; its id is still `profiles-carousel`. It shares Profile-first's gate, its photography and its per-profile config table, and inverts its layout: instead of one profile at full size with tabs to compare them, **every** profile is a full-bleed photographic card in a horizontal carousel, and the configuration that justifies it is hidden until you look. The other profiles concepts ask "what did we change for you"; this one asks "which of these do you want", and answers the first question only on demand.

**Being Plus-only means nothing on a card is locked**, so the two settings below the cards are live toggles rather than claims. **Continue below the carousel is the one exit** — per-card Connect was removed so picking a profile isn't presented as a mandatory action beside it.

**Every card gets its own narrated spinner → resolve reveal — requested explicitly, to restore the "personalization illusion" every other concept's settings rows already have.** An early version animated all cards in as a same-time stagger with no spinner phase at all; that read as one decorative sweep rather than as labor, so it was replaced. Each card now runs through `MaterializingSlot` (the exact same two-phase primitive every settings row elsewhere uses) shaped as a card: `CarouselCardPlaceholder` narrates *that specific profile* by name ("Personalizing your Streaming profile…") for `carouselCardSpinnerMs`, then crossfades into the finished `CarouselCard`. Cards resolve **strictly one at a time, never in parallel** — the whole point of a per-card spinner is to read as sequential labor, and six simultaneous spinners wouldn't. One profile's full cycle (spinner hold + crossfade + a settling pause before the next starts) sums to exactly 3000ms — each profile card takes 3 sec to generate; see `carouselCardSpinnerMs`/`carouselCardResolveMs`/`carouselCardGapMs` in `timing.ts`.

**Carousel entrance: cards slide in, not pop in.** Every other `MaterializingSlot` caller (rows, tiles, grid cards) only ever gains a NEW sibling below/after the one currently resolving, so that sibling's own fade+slide-up (`y: 8`, the default) is the only motion needed — nothing else on screen moves. A horizontal carousel is different: `CarouselTrack` centers its row (`justify-center`) until it overflows, so every time a new card mounts, the row's total width grows and **every already-resolved card's on-screen position shifts** to keep the row centered — without anything accounting for that, the shift was an instant jump the same frame the new card appeared, undercutting the "smoothly slide to the side" feel the sequential reveal is going for. Both `ProfilesCarouselConcept` and `ProfilesCarouselV2Concept` pass their `MaterializingSlot`s two opt-in props to fix this (see `MaterializingSlot.tsx`'s table entry above): `enterFrom="right"` (`x: 24 → 0` instead of the default `y: 8 → 0`, so a new card visibly arrives from the direction the track reads in, not from below) and `layoutAnimate` (Framer `layout="position"`, which animates ANY layout-box change of the slot — the centering recompute included — via FLIP, so the shift and the new card's own entrance play as one continuous slide rather than a jump-cut plus a fade). Both are opt-in rather than defaults on `MaterializingSlot` itself, since no other caller has this repositioning problem — their siblings never move when a new one mounts. Off under reduced motion (`layout={layoutAnimate && !reduced ? "position" : undefined}`), matching every other entrance in this file.

**On a run with more than 3 intents, `CarouselTrack` auto-scrolls to keep the card currently generating in view.** With 4+ profiles the carousel overflows, so once cards start resolving one at a time it's possible for the still-loading card to sit scrolled out of sight behind already-finished ones — the labor a user is watching for wouldn't be visible. `ProfilesCarouselConcept` derives `generatingIndex` (`cardStages.indexOf("spinner")` — at most one index ever matches, since cards resolve strictly sequentially) and passes it to `CarouselTrack` as `focusIndex`; the track calls `scrollIntoView({ inline: "nearest", block: "nearest" })` on that card whenever it changes. `"nearest"` on both axes is deliberate: it's a no-op whenever the card is already visible (a 1–3 intent run never triggers a scroll at all) and it never overrides a scroll position the user reached on their own by snapping to centre. `generatingIndex` is `-1` (mapped to `undefined`) during the short gap between one card resolving and the next starting, so the track holds still rather than jumping mid-pause.

**This is why the concept can't delegate to the shared `useTunedMaterialization`.** That hook assumes every "row" takes the same fixed duration; here the carousel's total duration is `profiles.length × 3000ms`, genuinely variable by selection size — a 6-intent run's carousel legitimately takes six times as long to finish building as a 1-intent run's, which the shared hook's fixed-per-row formula can't express without either starving a single profile of its full 3 seconds or bloating six profiles' reveal into a single profile's slot. `useProfilesCarouselData` therefore owns its own scheduling effect, but built from the SAME shared constants everywhere it can be: the identical header-intro timing (`T.centerHold`/`T.moveToTop`/`T.reducedIntroHold`), `T.rowGap`, `T.continueGapAfterTip`, and the same reduced-motion cadence — so switching between this concept and any other never feels like a pacing regression on the parts they do share. Sequencing: header lands → every card resolves one at a time → the two global setting rows rise in (only once every card has resolved) → Continue appears.

**The two global settings, and the rule that picks them.** `globalSettings.ts` resolves the app-wide settings shown below the carousel. A setting appears in exactly ONE place on this screen, enforced executably rather than by convention: `globalSettingsFor` filters its candidates against `PROFILE_CONFIG_LABELS`, so anything a card configures drops out automatically. A card reading "NetShield: Off" above a global toggle reading "NetShield — on" would read as a bug, not as a per-profile override. This is why the design's original NetShield toggle is **not** what ships here — the cards own NetShield.

- **Kill Switch is derived** — value from `mergeFreeSettings` (strictest across the selection, exactly as every other concept resolves it), sentence from the tone-voiced `outcomeForEnabled` the tuning rows already use. It is also the one free setting no card accounts for (cards carry Protocol but not Kill Switch), so surfacing it here completes the picture instead of repeating it.
- **Auto-connect is authored, and the only authored row** — sourced rather than invented: `ISPRegulationsPanel.tsx`'s recommended-actions list already carries this setting with this description and this `Wifi` glyph, so onboarding uses the wording the main app already uses. It has no `JTBD_TUNING_RESULT` entry because it isn't tuned per intent, which is exactly why it belongs below the cards rather than on one. **[UNVERIFIED]** — its tooltip is newly written.
- **The toggles are genuinely interactive**, not a decoration over a fixed value; turning one back off is a legitimate outcome of this screen. State is local to the row, so nothing persists into the main app. Under reduced motion the row starts on and the flip is skipped — a switch that silently changes value is worse than one that was always right.

**Copy** lives in the new `TUNING_CONCEPTS_COPY.profilesCarousel` key, and is the only concept's title/subtext that is **tone-constant** rather than drawn from `TUNING_COPY`. The shared titles describe the tuning as applied settings ("Tuned for your 3 interests") and each tone re-voices that framing; this concept's claim is the opposite — the outcome is a set of objects you were given — and no tonal variant of the shared copy says that. Same precedent as the profiles' own tone-constant `effectSentence`/`deltaSentence`. Its `counterText` returns the same steady line as `summaryText`: the line is a statement of fact true from the first card onward, so there is nothing for it to count up to, and holding it steady is what lets the cards carry the movement.

**Timing.** `TUNING_CONCEPT_TIMING` gained `carouselCardSpinnerMs` (2500), `carouselCardResolveMs` (300), `carouselCardGapMs` (200 — the three sum to the 3000ms-per-profile ask), `carouselRowRiseMs` and `carouselToggleFlipMs` and `carouselHoverMs`. `TUNED_RESULT_TIMING` is untouched.

### Profiles carousel v2 (Plus-only) — `concepts/profiles-carousel-v2/`

The twelfth concept, the third plan-gated one, and v1's carousel taken to its conclusion. v1 hedges: it shows the profiles as cards, then puts two app-wide setting rows underneath, so the screen says "here is what we changed" in parallel with "here is what you can use". **v2 drops the rows entirely.** The profiles are the outcome, there is nothing else on the screen, and every settings claim now lives inside the card it belongs to — reachable by hovering the profile it describes rather than listed separately from it. Concretely that buys 118px of card height (312 → 430) and a single answer to "what did you change" instead of two competing ones.

Both versions stay selectable. The two share v1's `CarouselTrack.tsx`, the reveal choreography and the screen's copy, and nothing else.

**The card (430×280).** Top-anchored identity block — a 52px gradient icon tile, then the profile name as a 26px title — then the disclosure region, then an opaque footer holding a country dropdown.

- **The disclosure is a crossfade inside a fixed region, not v1's height growth.** Both faces (chips and benefits) are absolutely positioned in the same 250px region, so they cross-fade in place and the title above them never moves. With up to six cards side by side, a card that grew on hover would shove its neighbours around — and the neighbours are what a user is comparing it against.
- **What the panel discloses is a benefit list, not the configuration** — see "Hover benefits" below. An earlier revision listed the six matrix settings and their values, each with an (i) tooltip; that list is what the benefit lines replaced.
- **The `onBlur` guard.** v1's card could use a bare `setFocused(false)` because it had no focusable elements inside the disclosure. v2 has the dropdown and its 99 options, so the handler checks `e.currentTarget.contains(e.relatedTarget)` — otherwise tabbing *within* the card would flicker the panel shut and open again on every step.
- **Hover is scoped to the identity/disclosure region only, `onFocus`/`onBlur` stay card-wide.** `onPointerEnter`/`onPointerLeave` live on the identity block (`ProfileIconTile` → title → the disclosure region), not the card's outer element — the country dropdown in the footer is a separate control, and a mouse hovering it (or its own popover, which portals outside the card) previously read as "hovering the card" and popped the benefit panel open behind it, which was never the intent. `onFocus`/`onBlur` are deliberately left on the OUTER card: tabbing from the disclosure into the dropdown is one continuous keyboard interaction with the card, unlike a mouse hover over an unrelated sibling, so focus keeping the panel open across that boundary is correct where hover doing the same isn't.
- **Two scrims and an opaque footer**, where v1 needs one gradient. v2's artwork is far brighter and more saturated: a top-weighted scrim carries the icon and title, a second one fades in only while open so the benefit list has a legible floor across all six illustrations, and the footer is fully opaque because a country name can't compete with whatever happens to be behind it in six different images.
- **`ProfileIconTile.tsx`** reuses the JTBD grid picker's own badge icon (`JTBD_ICONS`, `assets/jtbd-*.svg`) rather than building a third icon treatment — its `#EEBEFF`→`#6D4AFF` gradient is already baked into the artwork, so the card needs no gradient of its own. Shown at full colour, unlike the picker's grayscale-until-selected treatment, since this card has no unselected state to distinguish. (An earlier version built a square gradient tile behind a `lucide-react` glyph instead; replaced so the icon a user picked in the JTBD grid is recognisably the same badge here, rather than a lookalike redrawn in a different shape.) The OTHER existing icon set, `profile-icon-*.svg`, was never a fit regardless — it composites a country flag into the glyph, which would contradict the country dropdown three rows below it.

**Card height is the tightest number on the screen.** `ConceptFrame` spends 328px of the 768px window on chrome (Back, the 128px header block, its 30px gap, the 24px gap to Continue, Continue, and 40px of bottom padding) and `CarouselTrack` adds 2px, capping a card at 438. The 430 spent leaves the disclosure region 250px against a 177px worst case (Streaming — the only card carrying both the logo row and three benefit lines, each wrapping to two). Per-card Connect was removed, shrinking the footer from 100px to 52px and giving the benefit list the reclaimed room. This is also why `hoverSubtitle` is capped at ~34 characters and rendered with `truncate`: at 248px of text column a longer line wraps, which pushes that one card's divider and benefit list 18px below its neighbours', and six lists that don't align are six lists nobody can compare.

**The country dropdown is real, and per card.** It reuses `CountrySelect` (searchable, flagged, all 93 `countryMarkers` names) rather than a new control, extended with one optional prop: `ruleOptions`, the rule-based entries that describe a BEHAVIOUR rather than a place and so have no flag to show — "Fastest country", "Fastest P2P country", "Fastest (excluding my country)". Supplying them replaces the built-in `null` "Fastest country" entry; ids are namespaced `rule:…` so they can never collide with a country name. Hybrid's own call site is untouched and omits the prop entirely.

- Every card offers the same three rules plus every country — only the DEFAULT differs per profile, so a user who wants "fastest P2P" on the Streaming card can still pick it.
- State is local to each card and deliberately not lifted: one card's country has no business retargeting the other five, and it never touches the run's global `selectedCountry` either. The pick is illustrative — exit is via Continue below the carousel.
- The popover opens upward and is short enough (271px including its search field) to land inside the 330px above the trigger, which is what lets the card keep `overflow-hidden` for its own rounded corners.

The settings list answered "what changed"; a reviewer hovering a card is deciding between six profiles, and "NAT type: Moderate" only distinguishes them for someone who already knows what a NAT type is. Fixed labels in a fixed order made the six cards comparable field by field — a real property this loses — but field-by-field comparison is not the decision the screen is asking for. The tooltips went with the rows: a line that has to be explained isn't a benefit line yet.

Two rules keep the authored copy from drifting:

- **Every line is backed by a real `PROFILE_MATRIX` field**, cited in a trailing comment on that line. No claim may rest on a setting the matrix doesn't carry for that profile, and a matrix edit means revisiting the lines citing that field. NetShield is On for all six, so where it made the cut its line is phrased per intent ("Ad and tracker blocking on every stream" / "Ads and trackers blocked without added lag") rather than repeated verbatim; on profiles with three stronger, more distinguishing settings it's the one dropped, since a value every profile shares is the least useful thing a benefit line can say.
- **Length is structural.** The text column is 228px beside the check glyph (~34 characters), so every entry stays under ~50 characters and therefore under two lines. Three two-line entries, the divider and (on Streaming) the logo row fit comfortably in the 250px disclosure region — see the card-height note above.

The hover subtitles are deliberately not the profiles' existing `effectSentence`, which is a 20-plus-word sentence naming a destination the dropdown already states.

**Reveal choreography is v1's, unchanged** — each card runs its own narrated spinner through `MaterializingSlot` for the same 3000ms cycle, strictly one at a time, and `CarouselTrack` auto-scrolls to whichever is building. `useProfilesCarouselV2Data` is a fork of v1's hook rather than a parameterization, for one structural reason: v1's schedule ends with two setting rows rising in after the last card, and v2 has no rows, so completion (`rowsComplete`, and with it the header's checkmark, the summary line and Continue) hangs directly off the last card resolving. Every constant governing feel is still shared. The only durations v2 adds to `timing.ts` are the two `CardShimmer` values below, and neither touches the schedule.

**The generation shimmer and the freshness sweep (`CardShimmer.tsx`) — one visual doing two jobs, shared with the Free concept below.** A soft light band (10% white, 16px blur, tilted 18° off vertical, 60% of the card's width) travels diagonally through a card, clipped to its own rounded shape:

- **While the card is a placeholder it LOOPS** — a 700ms pass, a 200ms beat, repeat. That's what turns the placeholder from an empty slot with a spinner parked in it into a surface something is being done to: the spinner says "wait", the shimmer says "this is being made". The pass is deliberately short so roughly three of them fit inside `carouselCardSpinnerMs` (one inside the Free concept's shorter `spinnerHold`) — at a slower speed the loop would read as one sheen that happens to get cut off when the card resolves, rather than as a shimmer.
- **Once the card resolves the same band makes exactly ONE brighter pass** (16% white, 900ms, eased at both ends). This is the point of sharing one component between the two phases: the thing that was being made and the thing that arrived are visibly the same object, instead of a spinner that got replaced by a picture. It fires on mount, which *is* the resolve moment — `MaterializingSlot` mounts `resolvedContent` fresh when its stage flips — so there's no trigger to wire and the pass can never replay on a re-render.

On the resolved card the sweep is the **last child**, so it crosses the artwork *and* the opaque footer: the band belongs to the whole card, and stopping it at the footer's edge would give away that the card is layers rather than an object. It's `pointer-events-none`, so passing over the country dropdown can't intercept a hover or a click.

**Reduced motion gets nothing at all**, not a static gradient. The band deliberately carries no information — it doesn't indicate progress, position or time remaining — and the placeholder's narration already states what's happening in words, so switching it off costs nothing. (This is the same reasoning as `iconRowStagger`'s reduced-motion behaviour, not a new policy.)

**The generation dot field (`GenerationDotGrid.tsx`) — the assembly texture, and placeholder-only.** A canvas layer of ~1200 small white dots on a 10px grid, animated as a **procedural scan** rather than a continuous breath: every tick (a randomized 80–150ms) a random **3–8%** of the dots are picked and flared from the 0.15 resting opacity up to a per-flare peak of 0.7–1.0, rising over 150–300ms (cubic ease-in-out) and decaying back over `FALL_RATIO` × that rise (2.4×). The asymmetric envelope — snap on, drift off — is what reads as "being scanned" rather than "twinkling", and because a tick only writes to its own subset (and never retriggers a dot that's still climbing, which would stutter), the field is staggered and organic instead of blinking in unison. Dots not picked simply stay at rest; nothing is ever reset field-wide.

Canvas rather than DOM so ~1200 animated elements (`<div>` or `<circle>`) don't re-layout every frame. Nothing is created or destroyed per tick: the dot list is built once per layout, a tick writes four numbers onto each picked dot, and the draw is batched — every resting dot goes into a **single path with one `fillStyle`**, and only the handful currently flaring are filled individually. Selection samples with replacement so the per-tick cost tracks the ~36–96 dots actually picked, not the full grid.

Sits behind `CardHalo` and the spinner narration; the halo and shimmer layers still carry the "lit from within" and "band passing over" readings on top of it. **Reduced motion:** the grid still renders (it previously returned `null`), held as a single static frame at the 0.15 resting opacity — no ticks, no rAF loop, only the `ResizeObserver` redraw.

**The pulsating halo (`CardHalo.tsx`) — light from within, and placeholder-only.** A white `inset 0 0 48px 8px rgba(255,255,255,0.14)` shadow just inside the card's edge, breathing between 35% and 100% opacity on a 900ms cycle. It exists because a travelling band alone leaves the card completely inert between passes: the shimmer says something is passing *over* the card, the halo says something is going on *inside* it, and the dot field says something is being *assembled* — the card only reads as powered-while-empty with all three.

- **It's a separate component from `CardShimmer`, not a `mode="loop"` branch inside it.** The shimmer's sweep mode is used on resolved cards, so folding the halo in would mean gating it against the one mode it can never appear in.
- **It never reaches a resolved card**, by design rather than by current usage — a resolved card has artwork of its own to be lit by, and a permanent glow would turn a loading cue into decoration that never ends.
- **The pulse period equals `carouselShimmerLoopMs + carouselShimmerGapMs` exactly.** On the same cadence the travelling band and the breathing edge read as one thing lighting the card; two unrelated periods read as two animations that happen to share a surface.
- **It bottoms out at 35%, not 0** — a halo that drops out completely each cycle reads as a blink, i.e. as something switching on and off, where the point is a surface that stays lit and varies in how brightly.
- **It sits behind the narration** (the band stays in front), because it's the card's own lighting rather than something laid over its contents. And it animates **opacity, not the shadow**: interpolating a `box-shadow` string re-rasterizes a 48px blur every frame on up to six cards at once, while opacity on an already-composited layer doesn't.
- **Reduced motion degrades it rather than dropping it** — a steady glow is a perfectly good static visual, and only the pulsing is the part reduced motion objects to. (In practice phase 1 never mounts under reduced motion at all; the branch is so the component is correct on its own terms rather than only because of how it happens to be called.)

`TUNING_CONCEPT_TIMING` gained five keys for all of the above: `carouselShimmerLoopMs` (700), `carouselShimmerGapMs` (200), `carouselFreshnessSweepMs` (900), `carouselFreshnessStaggerMs` (90, used only by the Free concept) and `carouselHaloPulseMs` (900). All five are decorative in the strict sense — the loop and the halo run inside a placeholder's own spinner phase, and the sweep plays over a card that has already resolved — so no key can move a beat of the shared schedule. `TUNED_RESULT_TIMING` is untouched.

### Profiles carousel v2 — Free (Free-only) — `concepts/profiles-carousel-v2-free/`

The thirteenth concept, and the first gated the OTHER way (`FREE_ONLY_TUNING_CONCEPTS`). It exists because v2's Plus-only gate lets v2 decline the question every Free-capable concept has to answer: what does a Free user get out of this screen?

**Why v2 can't simply be rendered to a Free run.** Three reasons, all structural rather than cosmetic:

1. **Not one of the six profiles is deliverable on Free.** Checked against `PROFILE_MATRIX` field by field: Privacy needs Secure Core, Downloading and Gaming need P2P servers, Streaming needs the United States, Travel needs the United Kingdom, Bypass needs fastest-outside-country, and NetShield is On for all six. There is no subset of v2's profiles a Free run could honour, so there was never a "these ones are free" story waiting in the data — the free story had to be built.
2. **Only one of v2's six rendered rows is free.** `JTBD_TUNING_RESULT[jtbd].enabled` is a 2-tuple — Protocol and Kill Switch — and of v2's rows only Protocol comes from it. (Allow LAN is a v2-authored field that no part of the data models as free or paid. `[UNVERIFIED]`.)
3. **v2 deleted the only part of the screen a Free user could own.** v1 put two app-wide setting rows below the carousel, one of which (Kill Switch) is genuinely applied on every run. v2 traded them for 118px of card height. Restoring a free-owned register is the entire job of this concept.

**So this inverts v2's hierarchy rather than disabling parts of it.** v2's claim is that the profiles ARE the outcome and there is nothing else on the screen. Here the outcome is the two settings that were actually applied, stated first; the profiles sit below the boundary as a preview of what the upsell immediately after is selling. Both of the screen's non-negotiables are then satisfied honestly and by different halves of it: the settings carry the personalization illusion (they really happened), and the profiles carry the upsell bridge (real objects, correctly named, built from this user's own picks, and not yet theirs).

**The schedule — and the one place this concept is *simpler* than v1/v2.** It delegates to the shared `useTunedMaterialization` instead of owning a bespoke scheduling effect. Both Plus carousels had to fork because a per-card narrated 3000ms cycle makes total duration `cards × 3000ms`, which the shared hook's fixed-per-row formula can't express. Here the cards arrive as one group, so the schedule is three fixed-duration rows and the shared hook expresses it exactly:

1. `settingRows` (indices `0..s-1`) — the free settings, one at a time, narrated via the same `narrateEnabling` the default concept uses.
2. The boundary, at `boundaryIndex = s`. **Restored deliberately** — v2 pushes it past the end because nothing on a Plus run is locked, whereas here it is the exact beat where the screen stops describing what happened and starts describing what Plus would add.
3. The profiles as ONE row. Six narrated per-card cycles would be twelve seconds spent building things this user can't use, and "Personalizing your Gaming profile…" is a sentence a Free run has no right to. One group placeholder, then every card together.

**The card (280×240), and what was removed rather than disabled.** No Connect (a disabled button still promises a connection that can't happen), no country dropdown (93 countries and three rules, all Plus — a Free user picking one would be choosing between things they can't have), and no hover disclosure (with no Connect underneath, the settings panel is a spec sheet for a product this run doesn't have). What remains is what's still true: the artwork, the same `JTBD_ICONS` badge via v2's `ProfileIconTile`, the profile name, and the same derived `profileChips` — so the two versions are recognisably the same card rather than two designs sharing a name.

- **45% opacity on one layer, not per element.** The number is not new: it is exactly the treatment `CountryBrowser` already gives a Free user's locked profile rows, so a profile looks the same amount of unavailable here as it will in the sidebar minutes later. Applying it as a single layer is what makes the card read as "unavailable" rather than as several independently faded pieces of text.
- **The Plus badge sits outside that layer, at full strength.** It is the thing that explains the dimming, so dimming it too would leave the card faded for no stated reason. Boxed (border + scrim + blur) because it sits over six different illustrations.
- **The card is not interactive at all** — no hover state, no focus stop, nothing to click. Since the badge is then the only visual signal, each card also carries an `sr-only` "{name} — Available with VPN Plus" line, reusing `PLUS_AVAILABILITY_LABEL`.
- **The freshness sweep sits outside the dimmed layer too, at full strength.** This is the one place where dimming would cost the card something real: the sweep is how a Free user sees that these profiles were *built for them*, which is the entire reason they're on screen. Being unavailable and being freshly made are two different claims, and the card makes both.

**The loading effects, and the one thing they changed about the placeholder.** `CardHalo` and both phases of `CardShimmer` (all described in full under v2 above) apply here unchanged — a breathing inner glow and a looping band while the row is loading, then one brighter pass per card once they arrive. Two consequences specific to this concept:

- **The phase-1 placeholder became card-shaped** (`FreeCardsPlaceholder.tsx`): a single 280×240 box with a border and fill, centred in the row, rather than a spinner floating in a full-width empty band. The shape is what both effects need — a halo hugging an edge and a gradient masked inside a card outline read as a card being made, whereas the same two across a borderless region read as the page flashing. It's still **one** box rather than one per profile: a row of skeletons would imply each profile is being built separately, which is exactly the per-card beat the Plus carousel has and this concept deliberately doesn't. The box is a stand-in for "your profiles", matching `blockNarration`'s single line, and the real cards fan out from it.
- **The sweeps are staggered left to right** by `carouselFreshnessStaggerMs` (90ms × index). Only this concept needs it: its cards resolve as one group, and six identical sweeps firing on the same frame would read as a single screen-wide flash rather than as six cards each finishing. The Plus carousel resolves strictly one card at a time and so passes no delay.

**Card height is this screen's tightest number, same as in v2 but for different reasons.** `ConceptFrame` leaves 440px of body. Above the cards this concept spends ~84px on the two setting rows (`py-[10px]` rather than `StackedLayout`'s `py-[12px]` — the concept's one layout compromise), ~72px on `BoundaryDivider` (a shared component, so not ours to shrink) and 32px on `ConceptFrame`'s two 16px body gaps, leaving ~250px including `CarouselTrack`'s 2px. The 240 spent keeps ~10px in hand for a header title that wraps in a longer tone; past that the body scrolls rather than breaking, since `ConceptFrame`'s column is `overflow-y-auto`.

**Copy** lives in the new `TUNING_CONCEPTS_COPY.profilesCarouselV2Free` key and holds only three strings, because everything the SCREEN says comes from the shared tone-aware `TUNING_COPY`/`copy.ts` helpers — the opposite of v2, and deliberately. v2's tone-constant title claims the profiles are the outcome, which is the one claim a Free run can't make; the shared "Tuned for your N interests" says the right thing in all four tones.

- `profilesBandHeader(n)` — the boundary band's heading, in place of `plusSectionHeader`'s "More benefits for your interests available with VPN Plus". Names the count and the reason the cards are dim in one line, so the dimming is never unexplained. Its parenthetical is this band's own lowercased phrasing of `PLUS_AVAILABILITY_LABEL`, written out rather than composed from it (case-folding in code would also fold "VPN Plus").
- `blockNarration` — one line for the whole row, and it can't borrow v2's per-card narration for the reason given above.
- `carouselLabel` — the track's accessible name. Not `profilesCarousel`'s "Your personalized profiles"; that possessive is precisely what this run hasn't earned. This is the only reason `CarouselTrack` was touched at all: it gained an optional `label` prop defaulting to its existing string, so both Plus carousels are byte-for-byte unchanged.

**Continue has one destination** — the upsell — because a Plus run can never select this concept. That mirrors the Plus-only concepts' single destination exactly, and is why the component takes no `userPlan` and carries no plan branching internally.

## Multiple-mode tuning ("Selection" prototype control)

A prototype-only **"Selection"** dropdown (Single / Multiple, `App.tsx`, shown for the "tuning" stage) lets the JTBD picker select more than one intent. **Multiple is the default prototype experience** (`App.tsx`'s `selectionMode` state starts as `"multiple"`, confirmed) — Single remains fully supported and selectable from the same dropdown, and every underlying component's own prop default is still `selectionMode = "single"` (`JtbdGridPanel`, `TunedResult`), so nothing about Single mode's behavior changed, only which mode this top-level state starts as. Every Multiple-mode code path is gated behind `selectionMode === "multiple"` and, further, behind `selectedJtbds.length >= 2` (with exactly 1 selection, Multiple mode renders identically to Single mode — confirmed design: "1 selected → exactly as today" for every phase of this screen).

**Conflict analysis (confirmed at checkpoint):** since `JTBD_TUNING_RESULT` was reduced to its only 2 genuinely-tunable free settings (`"Protocol"` / `"Kill Switch"` — see the "Data model" entry above), a value conflict between selected JTBDs is now the COMMON case, not a rare edge case (e.g. Gaming's `"Standard"` Kill Switch vs. Privacy's `"Advanced"`). `SETTING_VALUE_PRIORITY` (`lib/jtbdMerge.ts`) resolves this with a "strictest wins" rule instead of a single-preferred-value lookup: Kill Switch's `"Advanced"` outranks `"Standard"` (Advanced's always-on block is a superset of Standard's drop-triggered one), and Protocol's `"Stealth"` outranks `"WireGuard UDP"` which outranks `"Smart"` (each is a superset of what the weaker value already does) — so the merged result is never a downgrade for any contributing JTBD's actual need. Note the row's `outcome`/`tooltip` text still follows the pre-existing "earliest-selected contributor wins" rule below, independent of which `value` strictness resolves to — see the open item under "Result curation" for why this can occasionally read as a slight mismatch.

**The picker (`JtbdGridPanel.tsx`):** new optional props `selectionMode`/`selectedMultiple`/`onToggleMultiple`, all defaulted so Single mode's own `selected`/`onSelect` path is untouched. Multiple mode: tiles toggle in/out of an ordered `selectedJtbds: JtbdId[]` (state lives in `OnboardingV2`, `toggleSelectedJtbd`); title/subtitle become "Pick what matters to you" / "Choose as many as apply. We'll tune Proton VPN for all of them." (`TUNING_COPY[tone].pickerTitleMultiple`/`pickerSubtitleMultiple`, tone-aware with the same `?? straightforward` fallback pattern as every other tone-aware string here — only `straightforward` has distinct content, confirmed at checkpoint as acceptable since full 4-tone variants for these were out of scope); the wink line shows the LAST-selected JTBD's line, fading out at 0 selections; the CTA is "Continue" (0 selected) / the existing `JTBD_CONTINUE_LABEL[jtbd]` (1 selected) / `"Tune for {count} interests"` (2+, confirmed phrasing). Each tile (`JtbdGridTile.tsx`) also gains a `multiple` prop (`false` in Single mode, unchanged there) that renders a top-left rounded-square checkbox indicator: unselected — a plain ring (`rgba(255,255,255,0.35)` border, transparent fill); selected — a filled purple (`#6d4aff`) rounded square with a white `lucide-react` `Check` glyph, matching the tile's own selected-border accent color.

**The merge engine (`lib/jtbdMerge.ts`):**
- `mergeFreeSettings(selectedJtbds)` — UNION of the selected JTBDs' `enabled` settings, deduplicated by `settingsName` via a `Map` (which preserves insertion order): each name is only ever INSERTED on its first encounter (so row order is "first-selected JTBD's rows in its own data order, then new unique rows from the second-selected, and so on", and the row's `outcome` text always stays the earliest-selected contributor's — this is what "the outcome sentence uses the earliest-selected contributor" means in code); later JTBDs contributing an already-seen setting can only affect its `value`, via the `SETTING_VALUE_PRIORITY` strictness comparison described above. Each returned `MergedEnabledFeature` also carries `primarySourceJtbd`/`primarySourceIndex` (for tone-outcome lookup) and `sourceJtbds` (informational). This is always the FULL, uncapped union (now capped at 2 rows by construction, since only 2 unique settings names exist at all) — see "Result curation" below for what trims it for display.
- `mergePaidFeatures(selectedJtbds)` — the same UNION/dedup convention as `mergeFreeSettings`, for the selected JTBDs' 2 `paid` features each (deduplicated by `featureName`; no conflict table needed — paid features have no `value` field to conflict over). Returns `MergedPaidFeature[]` (`sourceJtbds`/`primarySourceJtbd`/`primarySourceIndex`, same shape as `MergedEnabledFeature`).
- `buildProfilePreviews(selectedJtbds)` — one `ProfilePreview` (`jtbd`, `label` from `JTBD_PROFILE_LABEL`, `icon` from `JTBD_ICONS`) per selected JTBD, in selection order.
- `rankFreeSettings(merged)` / `rankPaidFeatures(merged)` — sort the full merged unions by the editorial `SETTINGS_RANK`/`FEATURES_RANK` maps (`lib/jtbdTuningResult.ts`, lower number = higher priority; confirmed at checkpoint — see "Result curation" below for the full order). `capList(ranked, cap)` then takes the top `cap` items and returns `{ displayed, overflow }` — the single shared truncation step both the free and Plus lists use.
- `outcomeForEnabled(tone, result, index, feature)` / `outcomeForPaid(tone, feature)` — the tone-voiced outcome lookups used by rendering; for a plain single-mode feature they're byte-for-byte the old `toneOutcome(tone, result.jtbdKey, kind, index)` call; for a merged feature they look up `toneOutcome(tone, feature.primarySourceJtbd, kind, feature.primarySourceIndex)` instead, since a merged row's index in the MERGED array is meaningless for tone lookup.
- `TuningResultLike` — a relaxed, structurally-compatible view of `JTBDTuningResult` (`enabled`/`paid` as plain arrays instead of fixed 2-/2-tuples) that all 4 layouts' `result` prop now accepts — tuples are assignable to arrays, so Single mode's real per-JTBD data needs no change; Multiple mode passes a synthetic `{ ...single, enabled: freeCapped.displayed, paid: [] }` (the CAPPED free list, not the full union).

**Result curation (capped/ranked lists — screen height stays stable from 1 to 6 selected interests):** the merged free-settings union now maxes out at 2 unique rows (`"Protocol"` / `"Kill Switch"`, well under `freeRowCap`), so `capList` never actually trims it today; the merged paid-features union can still grow to 12 across all 6 JTBDs, and IS trimmed. `TunedResult` ranks each union (`rankFreeSettings`/`rankPaidFeatures`) and caps the DISPLAY to the top items by editorial priority (`TUNED_RESULT_TIMING.freeRowCap` = 4, `paidFeatureCap` = 1 — tunable config, confirmed at checkpoint alongside the ranks themselves; `freeRowCap` is now a ceiling with headroom rather than an active limit, kept as-is rather than shrunk to 2 in case a future JTBD reintroduces a third free setting). The Plus section's total row count is therefore always exactly 2 — the profiles-summary row + 1 feature row (confirmed at checkpoint: "profile and something else depending on the selection").

**Completion counts match the DISPLAYED rows, not the true merged-union totals** (confirmed at a checkpoint, superseding this doc's earlier "always true totals" rule): the subtext's `{free} settings applied` reflects the merged free union's true size (1 free setting shared identically by every selected JTBD, or 2 once any two selected JTBDs' Protocol or Kill Switch values differ) — always ≤ `freeRowCap` (4), so never actually capped today. The `{features} features with VPN Plus` count is every row actually shown in the Plus section — the capped feature row(s) (`paidFeatureCap`, 1) PLUS the profiles row itself (always exactly 1 row, however many interests it lists) — so with the current cap this is always **2** (1 feature row + 1 profiles row), confirmed at checkpoint. Pluralization is handled (`summarySubtextMultiple`, `lib/toneOfVoice.tsx`) for the (now largely theoretical, since the count is always 2 today) singular case.
  - **`SETTINGS_RANK`** (`lib/jtbdTuningResult.ts`, confirmed order): Kill Switch (1) → Protocol (2). Kill Switch ranks first as the more protection-critical of the only 2 free settings that now exist.

**Open item — merged row copy vs. resolved value:** a merged row's `outcome`/`tooltip` always follows the earliest-selected contributor (per the dedup rule above), independent of which `value` the strictness comparison resolves to. E.g. selecting Gaming then Privacy merges Kill Switch to `"Advanced"` (Privacy's stricter value wins) while still showing Gaming's Standard-flavored outcome text ("Nothing leaves your computer unless it's protected") — not technically wrong, but not written to be value-agnostic either.   - **`FEATURES_RANK`** (confirmed order): NetShield (1) → Secure Core (2) → Streaming servers (3) → VPN Accelerator (4) → Server breadth (5) → P2P servers (6) → Port Forwarding (7) → Moderate NAT (8) → Fastest outside-country (9) → Network warning (10) → Home country profile (11) → Bypass profile (12).
  - **Completion counts match what's displayed** (see the checkpoint note above this list) — the subtext's `{N} settings applied`/`{M} features` are the DISPLAYED/capped counts, same as the live "Applying X of N" counter during materialization (`totalRows` = capped free + 1 profiles-summary row + capped Plus features) — both narrate what's actually on screen, not the full merged-union size.

Neither the FREE section nor the PLUS section shows this anymore — anything beyond the top 4 free settings (`SETTINGS_RANK`) or the 1 Plus feature (`FEATURES_RANK`) is simply not mentioned in the list. The completion subtext above the lists is still the true, honest total (see above) — only the per-section footnote was removed, not the honesty guarantee.

- **No existing toast/banner component to reuse** (confirmed at checkpoint): `components/ui/sonner.tsx` is dead shadcn/`sonner` scaffold, never mounted anywhere and tied to `next-themes` (not set up in this codebase, separate from the app's own `ThemeContext`) — building a small, self-contained component was confirmed as the right call rather than wiring that up.
- **Tone:** deliberately calm — no confetti/sound (that's the Plus-welcome screen's own moment, during onboarding itself, elsewhere), single sentence, no CTA/tips/upsell.

### Profiles spotlight (`components/ProfilesSpotlight.tsx`)

A one-shot coach mark shown the moment onboarding finishes handing off to the main app: the whole app window is dimmed except the sidebar's **Profiles list**, which is ringed in a glowing white border. It points at the profiles onboarding just generated and nudges a first connection through one of them.

- **Trigger:** `App.tsx`'s `handleEnterApp` arms `spotlightTimerRef` to call `showProfilesSpotlight` at `TRANSITION_TIMING.leftPanel.start + leftPanel.duration + 150`ms — right after the panel finishes sliding in, never during the entrance (the measurement would read a mid-animation position). Gated on `selectedJtbds.length > 0`, which is exactly the condition under which `CountryBrowser` opens on the Profiles tab with onboarding-generated rows, so it can never highlight a list with nothing personalized in it (skipped onboarding, "Go to app directly", the Tier 2/3 connection-failure exits all pass `[]`). Plan-agnostic: Free lands on the same generated (locked) profiles.
- **Measuring the region:** `App.tsx` owns a `profilesSectionRef`, threaded through `ISPRegulationsPanel` → `CountryBrowser` onto a **content block wrapping the Profiles tab from its header down to "New profile"**. That wrapper exists specifically for this — the scroll container around it stretches to the panel's full height, so measuring it would ring the empty space below the list too. `showProfilesSpotlight` subtracts the app window's own rect from the section's, so `spotlightRect` is in the window's coordinate space rather than the viewport's; a non-null `spotlightRect` IS the "spotlight is visible" state.
- **Rendering:** one `aria-hidden`, `pointer-events-none` element sized to the measured rect + 6px padding, at `z-[2000]` **at window level** (a sibling of the left panel, not inside it — the dim has to reach the map and the connection card, and the panel root is `overflow-hidden`). The cutout is an `absolute inset-0` child carrying `box-shadow: 0 0 0 9999px rgba(0,0,0,0.66)`: an outer shadow never paints inside its own border box, so the dim covers everything *except* the highlighted list, and the two can't drift apart because they're one layer. The white glow is a **second** child (rim `rgba(255,255,255,0.92)` + two bloom layers) rather than more entries in the same shadow stack, so it always paints over the dim instead of depending on shadow ordering. Its opacity breathes on a 2.1s loop; the 9999px spread is clipped by `vpn-app-container`'s `overflow-hidden`.
- **Dismissal:** after **5s** (`PROFILES_SPOTLIGHT_DURATION_MS`) or on **any click/keypress**, whichever comes first — the component registers `pointerdown`/`keydown` listeners on `window` in the capture phase (so a target that stops propagation can't trap it, and it clears on press rather than release) and calls `onDone` → `App.tsx`'s `dismissProfilesSpotlight`, which clears the arming timer and nulls `spotlightRect`. `AnimatePresence` fades it out. Because the overlay is `pointer-events-none`, the dismissing click still reaches whatever was under it — the spotlight informs, it never blocks.
- **Reduced motion:** `prefers-reduced-motion` drops the breathing loop; the dim and the white ring still render, still fade in/out, still dismiss the same two ways.
- **Relationship to the other landing surfaces:** independent of `WelcomeBanner` and `DeferredOnboardingBanner` (both in `WorldMap`'s banner slot) — nothing about their triggers or timing changed. Both sit outside the cutout, so they read as dimmed while the spotlight is up.
- **Banner copy:** the Profiles list's own inline banner (`PROFILES_ONBOARDING_BANNER_COPY.message`, `CountryBrowser.tsx`) sits inside the highlighted region and now carries the nudge: *"Connect through one of these profiles — each one is already tuned for what you told us matters."* (was *"We created these profiles from what you told us matters. Switch between them anytime."* — describing the profiles rather than prompting a connection). The Free-plan teaser banner (`PROFILES_PLUS_TEASER_BANNER_COPY`) is unchanged; it's an upgrade prompt, not a connect prompt.

### Deferred-onboarding banner (`components/DeferredOnboardingBanner.tsx`)

The Tier 3 landing's own banner — see "Connection failure path" above for the full behavior. ## Unprotected entrance animation ("surveillance lock-on")

The Unprotected screen plays a cinematic ~4.5s entrance on mount. The screen starts as the dark map only (everything else hidden) and reveals element by element while the map zooms toward the user. All timing lives in `lib/entranceTiming.ts` (`ENTRANCE_TIMING`).

Timeline (T=0 = mount):

| T (ms) | Element | Motion |
|--------|---------|--------|
| 0 | Map | Starts at world view (zoom 2), `flyTo` user coords (zoom 5) over 3500ms (Leaflet) |
| 500–2000 | Status gradient | Fades 0→1 (Framer) — danger tint creeps in |
| 1500 | Pin | Springs in (scale 0→1, overshoot) via CSS `ob2-pin-in` |
| 2000 | Pin pulsation | Concentric rings begin (CSS animation-delay) — not before |
| 2000 | Reticle | Animated targeting reticle scales/fades in (overshoot), then its layers animate continuously |
| 2500 | Padlock | Fade + drop from above |
| 2800 | Headline | Fade + slide up |
| 3100 | Subtext | Fade + slide up |
| 3200 | Info card | Rises from below |
| 3400 | Card rows | Stagger in 150ms apart (explicit per-row delays) |
| 4000 | CTA | Rises + scale; perpetual breathing glow (CSS `btnGlow`) |

Implementation notes:

- The map's `flyTo` starts at T=0 to the seeded fallback coords; when live IP detection resolves with different coords, a second `flyTo` (1.6s) redirects. The map never waits for the API.
- Pin entrance + pulsation gating are pure CSS (no setTimeout): the spring uses `animation-delay` = `pinAppear`; the pulse ring uses `animation-delay` = `bracketsStart`.
- `OnboardingMapV2` skips the first reactive run of its fly/status effects (`flyInit`/`statusInit` refs) so the mount entrance is not overridden.
- Info card shows skeleton bars (`loading` = unprotected && `!isLive`) and crossfades to real values when live data arrives. CTA is disabled (opacity 50%) until `isLive`.
- Per-phase delays are conditional: only `phase === "unprotected"` uses the long entrance delays; later phases use a quick stagger so transitions stay snappy.

## Phase-transition Choreography

- **Unprotected → Connecting** (button click): button scales/fades out; gradient coral→slate; padlock→spinner; reticle fades out (250ms); scramble starts +400ms; map zoom-out begins.
- **Connecting → Protected** (VPN confirmed, min 3.2s): spinner→lock; gradient slate→teal; `flyTo` server; teal pin; card rows stagger in; Continue fades in after.
- **Protected → JTBD** (Continue): centered overlay fades out; map dims; left column slides in from -40px, right from +40px.

## Stacking / z-index (important)

Leaflet assigns its internal panes z-index values of 200–700 (tilePane 200 … markerPane 600 … popupPane 700). Any overlay rendered as a sibling of the map must sit above this range or it will be painted over by the tiles (symptom: content flashes once, then the map covers it). v2 handles this by:

- isolating the Leaflet container with `isolation: isolate` so its pane z-indices stay contained, and
- rendering the centered overlay and the JTBD panel at `z-[1000]`, the title bar at `z-[1200]` (matching v1's convention).

## Prototype: Flow overview

A secondary **"View flow overview"** button sits below the start screen's primary "Start onboarding experience" (`App.tsx`, ghost/`border-white/20` style, matching `VPNPlusUpsell`'s "Continue free" convention — the primary button's own style/behavior is untouched). Both buttons are stacked vertically, same fixed width (`w-[320px]`) and same font size (`text-[17px]`/`leading-[22px]`), 16px apart, inside one shared glassmorphic container — `rgba(0,0,0,0.4)` + `backdrop-blur-md` (translucent, blurring the wallpaper behind it), rounded (`16px`), `24px` padding. Clicking the secondary button sets `AppState` to `"overview"`, rendering `FlowOverview` (`src/app/components/FlowOverview.tsx`) full-screen in place of the start screen; its top-left "Back" (same chevron+label affordance as `TunedResult`'s Back button) and Escape both return to `"start"`.

**Purpose:** a read-only diagram for a reviewer to understand the whole flow at a glance — what each stage is for and how it works. Titled **"Onboarding flow overview"**. It renders the 4 `ONBOARDING_STAGES` (`STAGE_ORDER` order) as equal-size cards in a horizontal row with connector chevrons between them (32px, `flex-col` → `lg:flex-row` responsive breakpoint stacks them vertically with downward connectors on narrow windows); a staggered fade+slide entrance (`staggerChildren: 0.07`, ~250ms per card, connectors fade in the same stagger sequence) plays once on mount — `prefers-reduced-motion` (via the shared `useReducedMotion` hook) drops to a plain fade with no stagger, nothing loops.

**Hover focus effect:** hovering any card scales it up (`whileHover={{ scale: 1.1 }}`) and dims every OTHER card to `opacity: 0.4`, so a presenter can visually isolate the card they're discussing. Driven by one `hoveredStage` state (not per-card `whileHover`, since dimming siblings needs to know what's hovered elsewhere); each card is split into an outer wrapper (owns the entrance stagger/opacity via `cardVariants`, untouched) and an inner wrapper (owns the hover scale + sibling-dim animation, `z-20` while hovered so the scaled-up card renders above its neighbors) so the two animations never fight over the same properties. Disabled entirely under `prefers-reduced-motion` (no scale, no dimming).

Each card shows, top to bottom: a real, representative **screenshot** of that stage (a full-bleed image spanning the card's own width via a negative-margin trick against the card's `p-[24px]` padding, clipped to the card's rounded corners by its `overflow-hidden`, `aspect-[4/3]` + `object-cover object-top`), then a 48×48px icon tile (`ShieldCheck`/`SlidersHorizontal`/`Settings2` from the already-installed `lucide-react` at 26px, or the real `vpn-plus-badge.svg` asset for "Upgrade to Plus" — no new artwork) sitting ABOVE the (`text-[19px]`) stage number + name line, then one fixed **Goal** sentence, and one fixed **How** sentence (both `text-[15px]`/`leading-[20px]`). The 4 screenshots (`src/app/assets/flow-overview/stage-{connection,tuning,upgrade,personalization}.png`, one representative screen from each stage's actual flow — connection's exposure screen, the JTBD picker, the VPN Plus upsell, and the "Set it up your way" modal) are looked up per stage via `STAGE_SCREENSHOT: Record<OnboardingStage, string>`. On wide windows (`lg:` and up) the row container has no upper width cap (`max-w-[1800px]`) and each card is `flex-1` (grows to fill the available row width, replacing an earlier fixed `w-[240px]`) — on narrow/stacked layouts each card instead caps at `max-w-[420px]` so it doesn't stretch edge-to-edge. The screen no longer shows a subtitle under the title, nor the live variation chips ("Version"/"Layout"/"Tone") or the "Testing: N x · M y" line that an earlier iteration had — removed per explicit request; `FlowOverview` now takes no props besides `onBack` and doesn't read the prototype's variation state (`variant`/`resultLayout`/`tone`) at all. All copy (title/labels/per-stage Goal+How sentences) is centralized in `FlowOverview.tsx`'s own `COPY` object, matching the i18n-ready convention every other prototype screen here uses (no framework exists in the repo). Cards are informational only — clicking one does nothing; there's no way to jump into a stage from this screen.
